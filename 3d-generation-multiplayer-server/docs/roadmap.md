# roadmap

Six phases. They are **clusters of functionality**, not a schedule. A phase is a
section of the software that holds together as one idea, and the numbering runs
foundational-first: later phases lean on earlier ones, and the last issue is a
capstone rather than an afterthought.

It is normal for the final issue completed to belong to phase 1.

---

## Phase 1 — The Tree That Isn't Ours

*Owning changes to code we did not write, without forking it.*

The first thing the vision asks for, and the floor everything stands on. Nothing
here is about the game; it is about being able to change a large C++ codebase
repeatedly, safely, and reversibly, for years.

The phase ends with an **unmodified** server running — a stock build, no patches
applied, databases populated, both daemons alive. That baseline is not a
stepping stone to be discarded; it stays reachable forever as the `stock`
profile, because every later breakage gets bisected against it.

| Issue | About |
|---|---|
| `101-the-tree-is-a-build-artifact` | the gitignore wire, the clone, the unconditional reset |
| `102-the-standard-patch` | the component shape: guard, anchor, marker, witness, match count |
| `103-the-orchestrator-and-profiles` | glob-sourcing, dispatch by naming convention, the profile table |
| `104-the-build-driver-and-the-trap` | apply → build → unapply, and the lock that advances only on success |
| `105-the-generators` | scaffolding a patch; regenerating the registry from headers |
| `106-the-verifier` | the round-trip and match-count assertions, wired as a gate |
| `107-the-pruning-machine` | retire, stale, review — computed on every upstream update |
| `108-a-stock-server-standing` | dependencies, databases, both daemons, and an account to log into |

## Phase 2 — The Handshake

*Proving we know a password we never send.*

The login conversation, headless. Six messages on one port, a well-defined
success condition, and no encryption on the socket to confuse matters. It ends
holding a forty-byte session key.

Every bug in this phase presents identically — *the proof did not match* — which
is why the arithmetic is split from the conversation and tested against known
vectors generated by running the server we already have.

| Issue | About |
|---|---|
| `201-the-packet-cursor` | bounds-checked reads and writes over a byte buffer, in one place |
| `202-the-modulus-and-the-power` | 256-bit modular exponentiation, little-endian in and out |
| `203-the-proof-without-the-password` | x, A, u, S, and the interleave that makes the session key |
| `204-the-six-messages` | the conversation as a state machine, errors named not swallowed |
| `205-the-realm-list` | learning where the world is, instead of being told at compile time |
| `206-a-key-in-hand` | **demo** — connect to stock upstream, print the realms and the key |

## Phase 3 — The World Stream

*A permanent duplex conversation, and a model of what exists.*

The larger protocol. Three layers that fail in three distinguishable ways, kept
apart on purpose. It ends with a program that has no window at all and can walk
a character in a square while printing everything it can see.

When this phase is done, the protocol work is finished, and every problem left
in the project is one we chose.

| Issue | About |
|---|---|
| `301-the-cipher-on-the-headers` | two keystreams from the session key, and the moment they engage |
| `302-the-variable-header` | one byte peeked, then three or four more; the mixed endianness |
| `303-opcodes-are-generated-not-typed` | extracting the table from the clone, so a rename cannot silently rot |
| `304-the-dispatch-table` | opcode to handler by index, with a default that names what it dropped |
| `305-getting-in` | the digest, character enumeration, entering the world |
| `306-the-update-block` | packed identifiers, mask blocks, and the movement structure |
| `307-the-world-model` | what exists, where, with what fields — fed by events, not by a socket |
| `308-moving-and-being-moved` | the movement family out, everyone else's movement in, the heartbeat |
| `309-a-character-walking-blind` | **demo** — headless, a square walked, everything visible listed |

## Phase 4 — The World of Shapes

*The first time anyone sees anything.*

Rendering, from an empty window to a world with people in it. Deliberately after
the protocol, so that a bug on screen can never be confused for a bug on the
wire — by this point the world model is already known to be correct.

This is the phase that makes the thesis real: rigid terrain, soft inhabitants.

Because the map format is the game's own, this phase does not wait on a world
being authored. The extraction tools produce a heightfield and a collision soup;
the collision soup is already triangles; we draw those. A real map, rendered as
abstract geometry, is the *first* thing on screen rather than the reward for
building a pipeline.

| Issue | About |
|---|---|
| `401-a-window-and-a-context` | SDL2, an OpenGL context, a frame loop, and a way to quit |
| `402-the-map-files` | the heightfield and the collision soup, read a tile at a time |
| `403-the-four-schemes` | palettes as tables, switchable by keypress, and the rule that no scheme is pink |
| `404-terrain-uploaded-per-tile` | flat-shaded triangles, one buffer per tile, normals from winding |
| `405-the-camera-question` | three cheap cameras, implemented so the choice can be looked at |
| `406-the-pink-star-squiggle` | the seed, the arms, the wander, the halo — **the visual thesis** |
| `407-the-trail` | a ring buffer sampled on a fixed interval, tapering into the past |
| `408-the-interface-of-one-verb` | click to move, click a thing, a visible timer, and nothing else |
| `409-first-sight` | **demo** — two clients, one world, two whisps that can see each other |

## Phase 5 — The Selection

*Choosing what the game is, without deciding what the server may never do.*

The vision's own words are about narrowing the default implementation. The
person's words about scope are what shape how:

> *"Assume that all the functionality is requested eventually, but we will only
> use some of it. I don't know what 'some' yet though."*

So this phase **selects rather than deletes**. The server keeps its systems;
what changes is what a player is granted, what the world contains, and what the
client exposes. "No abilities" means nobody is handed one and there is no button
— not that the code is torn out.

That is the cheaper shape in three ways: it is reversible, it conflicts with
nothing upstream (a deletion is the most fragile patch there is, fighting every
refactor of the thing it deletes), and it does not require knowing the final
subset in advance — which is the actual state of the design and the expensive
thing to pretend about.

| Issue | About |
|---|---|
| `501-the-seam-before-the-scalpel` | what a module hook can do from outside, and what genuinely needs reaching in |
| `502-granting-nothing` | no abilities, as a matter of what is handed out rather than what exists |
| `503-the-waiting-verb` | gathering, which already works; what the client shows of it and what it does not |
| `504-potions-and-better-equipment` | the two systems the game actively uses |
| `505-the-exposure-boundary` | written down: what the client implements, and what stays present and silent |
| `506-a-world-of-our-own` | authoring a custom map into the existing format, and registering it |
| `507-the-selected-server-standing` | **demo** — the same client, the same walk, against a server configured into a different game |

## Phase 6 — One Project

*The client and the engine stop being two projects that agree on a format.*

The liberation the vision names — which is that **our** client works, well
enough that nothing else is needed. Not that the protocol is replaced: if all of
the original functionality may eventually be wanted, then throwing away the
messages that carry it would be paying twice for the same ground.

So the move here is extension, not replacement. Where the game we have built
needs something the protocol has no message for, we add a message. Where it
does not, we keep what works.

| Issue | About |
|---|---|
| `601-what-the-protocol-does-not-carry` | measuring what we need and it cannot say, before designing anything |
| `602-messages-of-our-own` | new opcodes alongside the old ones, on both sides, as patches and client code |
| `603-the-world-built-with-it` | an authored world, played in, that could not have been made before |
| `604-the-documentation-pages` | generated HTML, everything linked to everything, in the project's own look |
| `605-the-output-gate` | writing goodbye, which is how a program ends |
| `606-the-client-and-the-server-in-one-tree` | **capstone** — one project, one build, one thing |

## The shape of the dependency

    Phase 1 ──────────────────────────────────────▶ everything
       │
       ├────────────────┐
       ▼                ▼
    Phase 2 ──▶ Phase 3 ──▶ Phase 4
                    │           │
                    └─────┬─────┘
                          ▼
                       Phase 5 ──▶ Phase 6

Phases 1 through 3 produce something genuinely useful with no graphics at all: a
server we can change safely, and a headless client that proves the changes did
not break anything. That is the point of ordering it this way. Phase 4 is the
first phase whose absence would be *felt*, and it is deliberately not first.

## Open questions

Not decoration, and not a closing section written once and abandoned. Each of
these surfaced while writing the documents above, and each one changes what gets
built. They get worked through one at a time; a phase holding an unanswered
question that belongs to it is in progress, not finished.

### Live

**Q1 — Is there a copy of the client's data to extract from?**
The most immediately blocking question in the project, and it blocks in two
places at once. The server will not start without the extracted data tables and
map files; phase 4's whole "a real world, free, on day one" depends on the same
archives. Everything before that point — the entire patch machine — is
unaffected, so this does not stop work starting. *(Blocks: `108`, and all of
phase 4.)*

**Q2 — Multicolour, or pink?**
The vision says characters are *multicolour* whisps; the person said *pink*. The
proposal on the table: pink is the constant shared form, and per-character
variation lives in a secondary hue at the arm tips, derived from the same seed.
So every whisp is unmistakably a pink star squiggle and no two are identical.
*(Blocks: `406`.)*

**Q3 — Which camera?**
Overhead, isometric, and behind-the-shoulder make three different games from
identical geometry, and the vision does not say which. `405` implements the
cheap version of each so the question can be answered by looking rather than by
arguing. *(Blocks: `408`.)*

**Q4 — Write the big-number arithmetic, or link the library?**
A 256-bit modular exponentiation is a few hundred lines of C with no
constant-time discipline needed, and it is one of the places where "can you
write this part in assembly?" has an obviously interesting answer. Linking what
the server already depends on is faster to a working login. *(Blocks: `202`.)*

**Q5 — What does the client do with a message it does not implement?**
Given that all of the original functionality may eventually be wanted, the
unhandled case is not an error — it is a *not yet*. Log the name and drop, log
once per opcode and drop, or record unhandled traffic to a file so the shape of
what we are ignoring can be measured before deciding what to implement next?
The third turns the exposure boundary into something observed rather than
guessed. *(Blocks: `304`, `505`.)*

**Q6 — How many people, at once?**
Nothing in the design is sized yet. The answer changes whether the whisp
generation loop ever needs threading, and whether the server's own tuning is
worth touching at all.

**Q7 — Which upstream commit, and how often do we chase it?**
The pruning machine exists precisely so updating is cheap, but cheap is not
free. Pin and update deliberately, or track the default branch and let the audit
say what moved?

### Answered

**Does "generation" mean the world is generated?** — Set aside. *"Doesn't matter
at this point, just use the same map file format that 3.3.5a uses and we're good
to build whatever we want on it later."* Authored, generated, or grown are all
reachable from the same format, so the question does not need answering before
the format is in use.

**Which bridge to server-side collision?** — Keep the existing format and
inherit its whole toolchain unchanged. The extraction tools and the
navigation-mesh builder are used as they are. This dissolved what had been the
largest fork in the project, and it handed phase 4 a free first world along the
way.

**Where does the waiting verb's clock live?** — Dissolved by selection rather
than deletion. The spell system stays, gathering works as it always did, and a
player cannot cast anything because nobody handed them anything.

**Are there creatures?** — Deferred on purpose. *"We will build things slowly
bit by bit."* Nothing in phases 1 through 4 depends on the answer, and the
navigation mesh comes free with the format decision either way.

**The first commit, in a shared repository.** — Commit only our own paths and
our own lines; leave everyone else's staged and modified work untouched.
