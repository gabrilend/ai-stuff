# roadmap

Seven phases. They are **clusters of functionality**, not a schedule. A phase is
a section of the software that holds together as one idea, and the numbering
runs foundational-first: later phases lean on earlier ones, and the last issue
is a capstone rather than an afterthought.

It is normal for the final issue completed to belong to phase 1.

---

## Phase 1 — The Tree That Isn't Ours

*Owning changes to code we did not write, without forking it.*

The first thing the vision asks for, and the floor everything stands on. Nothing
here is about the game; it is about being able to change a large C++ codebase
repeatedly, safely, and reversibly, for years.

The phase ends with the **login server** running against an unmodified build.
That daemon needs no client-derived data at all, which is what lets phase 1
finish cleanly before the data problem is touched. The stock profile stays
reachable forever, because every later breakage gets bisected against it.

| Issue | About |
|---|---|
| `101-the-tree-is-a-build-artifact` | the gitignore wire, the clone, the unconditional reset |
| `102-the-standard-patch` | the component shape: guard, anchor, marker, witness, match count |
| `103-the-orchestrator-and-profiles` | glob-sourcing, dispatch by naming convention, the profile table |
| `104-the-build-driver-and-the-trap` | apply → build → unapply, and the lock that advances only on success |
| `105-the-generators` | scaffolding a patch; regenerating the registry from headers |
| `106-the-verifier` | the round-trip and match-count assertions, wired as a gate |
| `107-the-pruning-machine` | retire, stale, review — computed on every upstream update |
| `108-a-login-server-standing` | **demo** — dependencies, databases, an account, and a daemon answering |

## Phase 2 — The Handshake

*Proving we know a password we never send.*

The login conversation, headless, against the daemon phase 1 left running. Six
messages on one port, a well-defined success condition, and no encryption on the
socket to confuse matters. It ends holding a forty-byte session key.

Deliberately before the data problem: it is a complete, satisfying piece of the
client that depends on none of it.

Every bug in this phase presents identically — *the proof did not match* — which
is why the arithmetic is split from the conversation and tested against known
vectors generated by running the server we already have.

| Issue | About |
|---|---|
| `201-the-packet-cursor` | bounds-checked reads and writes over a byte buffer, in one place |
| `202-the-modulus-and-the-power` | 256-bit modular exponentiation, little-endian in and out |
| `203-the-proof-without-the-password` | x, A, u, S, and the interleave that makes the session key |
| `204-the-six-messages` | the conversation as a state machine, errors named not swallowed |
| `205-the-realm-list` | learning where the world is, instead of being told at compile time |
| `206-a-key-in-hand` | **demo** — connect to stock upstream, print the realms and the key |

## Phase 3 — The Fabricated Data

*Everything the server expects a client to have provided, made instead.*

There is no copy of the original client and there will not be one. The world
server will not start without the client-derived data tables — this is a refusal,
not a degradation — so they get generated.

The phase rests on one fact: **the server's own source defines the layout of
every file it loads.** The loader's format descriptors are the schema, in the
tree we already clone. Nothing is transcribed; everything is extracted.

Two things make this smaller than it sounds. The world database — creatures,
items, quests, spawns — ships as SQL with the server and was never client data.
And the height format has a flag meaning *this tile is flat*, under which there
is no grid to generate at all.

| Issue | About |
|---|---|
| `301-the-schema-extractor` | upstream headers into layouts, as data; the third use of this pattern |
| `302-the-table-writer` | header, records, string block — and the seventeen-column localised-string trap |
| `303-round-trip-or-nothing` | generate, read back with the same schema, compare; a gate |
| `304-the-minimum-set` | measuring which tables the server actually demands before it will boot |
| `305-flat-ground` | the height format, and the flag that means there is no grid |
| `306-a-map-that-exists` | the map row, one area, and moving the starting position onto it |
| `307-a-world-server-standing` | **demo** — a world server boots on data no client ever touched |

Collision and navigation are **not** in this phase. Both are switchable off in
the server's own configuration, and neither is needed to stand on flat ground.
They arrive in phase 5, when there is something worth colliding with — and the
navigation mesh is never written at all, because the server's own tool builds it
from the other two.

## Phase 4 — The World Stream

*A permanent duplex conversation, and a model of what exists.*

The larger protocol, against the world server phase 3 got booting. Three layers
that fail in three distinguishable ways, kept apart on purpose. It ends with a
program that has no window at all and can walk a character across flat ground
while printing everything it can see.

When this phase is done, the protocol work is finished, and every problem left
in the project is one we chose.

| `402-the-variable-header` | one byte peeked, then three or four more; the mixed endianness |
| `403-opcodes-are-generated-not-typed` | extracting the table from the clone, so a rename cannot silently rot |
| `404-the-dispatch-table` | opcode to handler by index, with a default that names what it dropped |
| `405-getting-in` | the digest, character enumeration, entering the world |
| `406-the-update-block` | packed identifiers, mask blocks, and the movement structure |
| `407-the-world-model` | what exists, where, with what fields — fed by events, not by a socket |
| `408-moving-and-being-moved` | the movement family out, everyone else's movement in, the heartbeat |
| `409-a-character-walking-blind` | **demo** — headless, a square walked, everything visible listed |

## Phase 5 — The World of Shapes

*The first time anyone sees anything.*

Rendering, and the geometry that feeds both halves. Deliberately after the
protocol, so a bug on screen can never be confused for a bug on the wire — by
this point the world model is already known to be correct.

This is also where the flat ground of phase 3 gains shape: geometry authored in
text becomes both the collision the server believes in and the triangles we
draw. One source, two consumers, no second copy to drift from.

This is the phase that makes the thesis real: rigid terrain, soft inhabitants.

|---|---|

| `502-geometry-authored-in-text` | the shape format: quads, triangles, boxes, palette slots |
| `503-shapes-become-collision` | our geometry into the game's collision format, and the navmesh tool run over it |
| `504-the-four-schemes` | palettes as tables, switchable by keypress, and the rule that no scheme is pink |
| `505-terrain-uploaded-per-tile` | flat-shaded triangles, normals from winding, one buffer per tile |
| `506-the-camera-question` | three cheap cameras, implemented so the choice can be looked at |
| `507-the-pink-star-squiggle` | the seed, the arms, the wander, the halo — **the visual thesis** |
| `508-the-trail` | a ring buffer sampled on a fixed interval, tapering into the past |
| `509-the-interface-of-one-verb` | click to move, click a thing, a visible timer, and nothing else |
| `510-first-sight` | **demo** — two clients, one world, two whisps that can see each other |

## Phase 6 — The Selection

*Choosing what the game is, without deciding what the server may never do.*

The vision's words are about narrowing the default implementation. The person's
words about scope shape how:

> *"Assume that all the functionality is requested eventually, but we will only
> use some of it. I don't know what 'some' yet though."*

So this phase **selects rather than deletes**. The server keeps its systems;
what changes is what a player is granted, what the world contains, and what the
client exposes. "No abilities" means nobody is handed one and there is no button
— not that the code is torn out.

That is cheaper in three ways: it is reversible, it conflicts with nothing
upstream (a deletion is the most fragile patch there is, fighting every refactor
of the thing it deletes), and it does not require knowing the final subset in
advance — which is the actual state of the design and the expensive thing to
pretend about.

| Issue | About |
|---|---|
| `601-the-seam-before-the-scalpel` | what a module hook can do from outside, and what genuinely needs reaching in |
| `602-granting-nothing` | no abilities, as a matter of what is handed out rather than what exists |
| `603-the-waiting-verb` | gathering, which already works; what the client shows of it and what it does not |
| `604-potions-and-better-equipment` | the two systems the game actively uses |
| `605-the-exposure-boundary` | written down: what the client implements, and what stays present and silent |
| `606-a-world-of-our-own` | an authored world, with its own tables, that is nobody else's place |
| `607-the-selected-server-standing` | **demo** — the same client, the same walk, against a server configured into a different game |

## Phase 7 — One Project

*The client and the engine stop being two projects that agree on a format.*

The liberation the vision names — which is that **our** client works, well
enough that nothing else is needed. Not that the protocol is replaced: if all of
the original functionality may eventually be wanted, throwing away the messages
that carry it would be paying twice for the same ground.

So the move is extension, not replacement. Where the game we have built needs
something the protocol has no message for, we add a message.

| Issue | About |
|---|---|
| `701-what-the-protocol-does-not-carry` | measuring what we need and it cannot say, before designing anything |
| `702-messages-of-our-own` | new opcodes alongside the old ones, on both sides |
| `703-the-world-built-with-it` | a place played in that could not have been made before |
| `704-the-documentation-pages` | generated HTML, everything linked to everything, in the project's own look |
| `705-the-output-gate` | writing goodbye, which is how a program ends |
| `706-the-client-and-the-server-in-one-tree` | **capstone** — one project, one build, one thing |

## The shape of the dependency

    Phase 1 ────────────────────────────────────────────▶ everything
       │
       ├──────────────┬───────────────┐
       ▼              ▼               │
    Phase 2 ──▶ Phase 3 ──▶ Phase 4 ──▶ Phase 5
                                           │
                                           ▼
                                        Phase 6 ──▶ Phase 7

Phase 2 needs only the login daemon, which needs no fabricated data — so it can
run alongside or ahead of phase 3 rather than waiting on it.

Phases 1 through 4 produce something genuinely useful with no graphics at all: a
server that can be changed safely, a server that boots on data nobody extracted
from anything, and a headless client that proves neither is broken. That is the
point of ordering it this way. Phase 5 is the first phase whose absence would be
*felt*, and it is deliberately not first.

## Open questions

Not decoration, and not a closing section written once and abandoned. Each of
these surfaced while writing the documents above, and each one changes what gets
built. They get worked through one at a time; a phase holding an unanswered
question that belongs to it is in progress, not finished.

### Live

**Q1 — Multicolour, or pink?**
The vision says characters are *multicolour* whisps; the person said *pink*. The
proposal on the table: pink is the constant shared form, and per-character
variation lives in a secondary hue at the arm tips, derived from the same seed.
So every whisp is unmistakably a pink star squiggle and no two are identical.
*(Blocks: `507`.)*

**Q2 — Which camera?**
Overhead, isometric, and behind-the-shoulder make three different games from
identical geometry, and the vision does not say which. `506` implements the
cheap version of each so the question can be answered by looking rather than by
arguing. *(Blocks: `509`.)*

**Q3 — Write the big-number arithmetic, or link the library?**
A 256-bit modular exponentiation is a few hundred lines of C with no
constant-time discipline needed, and it is one of the places where "can you
write this part in assembly?" has an obviously interesting answer. Linking what
the server already depends on is faster to a working login. *(Blocks: `202`.)*

**Q4 — Keep the shipped identifiers, or invent our own?**
The world database ships with the server and references races, classes, maps,
and displays by number. Reusing those numbers keeps that SQL usable for free;
inventing our own means owning the rewrite. The plan is to keep them at first
and diverge only when something is gained — but that "at first" wants a
deliberate decision about when. *(Blocks: `306`, `606`.)*

**Q5 — What does the client do with a message it does not implement?**
Given that all of the original functionality may eventually be wanted, the
unhandled case is not an error — it is a *not yet*. Log the name and drop, log
once per opcode, or record unhandled traffic to a file so the shape of what we
are ignoring can be *measured* before deciding what to implement next? The third
turns the exposure boundary into something observed rather than guessed.
*(Blocks: `404`, `605`.)*

**Q6 — How many people, at once?**
Nothing in the design is sized yet. The answer changes whether the whisp
generation loop ever needs threading, and whether the server's own tuning is
worth touching at all.

**Q7 — Which upstream commit, and how often do we chase it?**
The pruning machine exists precisely so updating is cheap, but cheap is not
free. Pin and update deliberately, or track the default branch and let the audit
say what moved?

### Answered

**Is there client data to extract from?** — No, and there will not be. Everything
the server expects to have been extracted gets fabricated instead, from schemas
read out of the server's own source. This added a phase and made the project
strictly better: a server fed extracted retail data is still bound to that
client at one remove, and one fed data we generated is not bound to it at all,
which is the vision's own word for what it wants.

**Does "generation" mean the world is generated?** — Set aside. *"Doesn't matter
at this point, just use the same map file format that 3.3.5a uses and we're good
to build whatever we want on it later."* Authored, generated, or grown are all
reachable from the same format.

**Which bridge to server-side collision?** — Keep the existing format and
inherit its toolchain unchanged. The navigation-mesh builder consumes height and
collision data, so producing those two is the whole job and the
hardest-sounding artifact costs nothing.

**Where does the waiting verb's clock live?** — Dissolved by selection rather
than deletion. The spell system stays, gathering works as it always did, and a
player cannot cast anything because nobody handed them anything.

**Are there creatures?** — Deferred on purpose. *"We will build things slowly
bit by bit."* Nothing before phase 6 depends on the answer.

**The first commit, in a shared repository.** — Commit only our own paths and
our own lines; leave everyone else's staged and modified work untouched.
