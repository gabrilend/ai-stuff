## Current behavior

Nothing. The dunes are designed to be drawn from the heightfield directly —
shading by height and slope, the water line, the hydrocarbon marks — by issue
602, and that is enough to read the ground. The vision asks for more: a field
whose art is generated by an image model, because the field is random every
match and the number of dune shapes it can take would exhaust any hand-drawn
tileset. Nothing generates images, and no document commits to how.

## Intended behavior

**Design pending until the viewer exists.** This issue is a blueprint for a
pipeline whose inputs and outputs are decided now and whose middle — which
image model, how it is asked — is decided when there is a ground layer to lay
the result on and a person to look at it. What is decided:

**It is a tool that writes assets, and the viewer only loads them.** The
pipeline lives under `scripts/`, runs on a workstation, and writes a numbered
tileset into `assets/`. It is never run by the game, never run at match time,
and never run on the handheld. The heightfield is random every match; the
tileset is generated once, looked at, kept, and reused across every match —
which is the vision's point: an artist would have to draw every shape, a tool
draws each *class* of shape once and the ground layer picks.

**The input is a set of tile classes read off the heightfield.** A cell's class
is a small integer computed from the numbers the field already holds: its
height band, the steepness of its slope, which way the slope faces against the
field's wind, whether it is shore or water, whether it is a hydrocarbon seam.
The classes are a table in the pipeline and the ground layer alike — one file,
read by both — so the tool and the viewer cannot disagree about what a crest
is. Each class is described in words, and those words are what the tool hands
the image model, together with the site's palette and the tile's size.

**The output is images and a manifest.** For each class, one or more tile
images — variants, so that a long trough is not one tile repeated — and one
manifest table in `assets/` naming, per class, its image files, its variant
count, the tile size in pixels, and the provenance: which model, which prompt,
which seed, when. The manifest is a Lua table like every other catalogue, with
a companion, and the ground layer reads it and nothing else.

**Every tile ever made is kept and rated.** Generated images are not thrown
away when a better one arrives; they go into a pool, each rated on one scale by
a person and by a machine, and the tool draws from the pool by rating when it
assembles a tileset. A tileset that is looking bad is improved by rating, not
by regenerating from nothing. That is the monorepo's canvas-and-paintbrush
discipline, and this pipeline is an instance of it.

**The ground layer's change is small.** Issue 602's shading stays as the
fallback that is not a fallback: with no tileset in `assets/` the layer shades;
with one, it blits the class's tile, chosen by variant from a named random
stream so the choice is the same on every machine. A tileset whose manifest
names a missing image is a load-time error naming the class.

## Suggested implementation steps

1. Write the class table as a numbered file under `src/` with a companion: the
   function from a cell's neighbourhood in the heightfield to a class integer,
   and the words for each class. Issue 602's layer and the pipeline both load it.
2. Write the pipeline's frame under `scripts/`: read the class table, read a
   configuration from `input/` naming the model, the tile size, and the variant
   count; write the manifest; refuse by name when anything is absent. The step
   that asks a model for an image is one function, folded, marked as the part
   this issue leaves pending.
3. Write the pool: a directory under `assets/` where every generated tile lands
   with its class, its prompt, its seed, and its rating, and the assembly step
   that picks the best-rated variants per class into the manifest.
4. Extend issue 602's ground row: if a tileset manifest exists, blit tiles by
   class and variant; if not, shade. Both paths tested with no window.
5. Decide the model and the prompt with a person looking at tiles on the ground
   layer, then close this issue's pending part and record what was chosen in
   the manifest's provenance.
6. The test: the class function is deterministic and covers every class for the
   test field; a manifest naming a missing image is refused by name; the ground
   row with a tileset and without both return pixel data of the right size.

## Still open

- Which image model, run where, asked how. Pending the ground layer and a
  person.
- How a tile is made to join its neighbours without a visible seam — whether
  the model is asked for tileable images, or edges are blended by the
  pipeline, or the classes are chosen so that transitions are tiles of their
  own. The third is the most work and the most honest.
- How many classes. Too few and the dunes look like a pattern; too many and
  the pool is never rated. A number for the ledger once tiles exist.
