# Issue #022: Classify harness envelope traffic in transcripts

## Current Behavior

A session log records more than a conversation. Alongside what the user typed
and what the model replied, Claude Code writes **envelope traffic** into the
same log: machine-authored messages that occupy the user's seat because that
is the only seat available for text addressed to the model.

The conversation parser (`libs/conversation-parser.lua`) has one rule for
deciding what is a user turn: a message of type `user` whose content is not a
tool result. Every piece of envelope traffic passes that test, so all of it is
emitted under a `### User Request N` heading, indistinguishable from something
the user actually wrote, and consuming a number in the same sequence.

### What the envelope traffic actually is

Counted across every transcript under `ai-stuff/*/llm-transcripts/` and
`ai-stuff/*/*/llm-transcripts/`:

| kind | transcripts affected | what it looks like |
| --- | --- | --- |
| local-command caveat | 46 | The boilerplate `Caveat: The messages below were generated by the user while running local commands. DO NOT respond to these messages…`, wrapped in a `<local-command-caveat>` tag. Frequently the entire body of the block, with no content after it. |
| compaction recap | 42 | `This session is being continued from a previous conversation that ran out of context. The conversation is summarized below:` followed by a long machine-written analysis of the work so far. |
| slash-command scaffolding | 37 | `<command-name>/config</command-name>` plus `<command-message>` and `<command-args>` tags, and separately `<local-command-stdout>` / `<local-command-stderr>` blocks carrying the command's output. |
| empty numbered blocks | roughly 20 | A `### User Request N` heading with no body at all. |

The empty blocks have their own mechanical cause, separate from the others.
The routine that writes a user turn only handles content that arrives as a
plain string. When a message's content arrives instead as a **list of content
blocks**, the heading and the horizontal rule are written but the body is
skipped, because no branch handles the list case. The messages that take that
shape are system-injected notices — observed examples are `Browser tools are
not available in this session` and `[Request interrupted by user]`. No
user-typed text has been observed taking this shape, so nothing the user wrote
is currently being lost this way; the result is numbered ghosts that inflate
the request count. Two are visible in
`ai-playground/ceramic-trainstation/llm-transcripts/jul-29-26_agent-1.md` at
lines 246 and 251.

### Which slash commands actually appear

From every surviving session log (a 30-day window, so this is a sample rather
than a census):

| command | invocations |
| --- | --- |
| `/model` | 25 |
| `/compact` | 5 |
| `/usage` | 3 |
| `/config` | 3 |
| `/extra-usage` | 2 |
| `/remote-control` | 1 |
| `/login` | 1 |
| `/clear` | 1 |

### Why this is a problem worth naming

The transcripts exist so that someone reading them can see how a project was
designed, and design the same way if they want to. That purpose is served by
the decisions and the reasoning behind them. It is not served by a record of
the user opening a settings dialog and dismissing it, and it is actively
harmed when a numbered heading promises a user request and delivers harness
boilerplate that says, in its own text, not to pay attention to it.

## Intended Behavior

The transcript is **a record of what the model was told, without losing what
the user said.** It keeps what changes the course of the work and discards
what does not. It reads as a narrative explaining how the project developed —
not as a work log, and not as an attribution record.

That purpose supplies the test for every piece of envelope traffic:

> Does this change the course of what happens next?

Applying that test to what is actually in the corpus gives three groups.

### Group one — dropped, because the course does not turn on them

- **Local-command caveat boilerplate.** It is plumbing whose own text
  instructs the reader to disregard it. It contains no information about the
  project.
- **Housekeeping slash commands and their confirmations**: `/usage`,
  `/config`, `/extra-usage`, `/login`, `/remote-control`, along with outputs
  such as `Settings dialog dismissed`, `Stats dialog dismissed`, and
  `Login successful`. Checking a usage figure or dismissing a dialog leaves
  the work exactly where it was.
- **System-injected notices that produce empty blocks**, such as the
  browser-tools availability notice.

### Group two — kept, but labelled as what they are

- **Compaction recaps.** These stay in full. They are useful and wanted. What
  changes is only the heading: a recap presented as `### User Request 8`
  claims the user wrote a long technical analysis they did not write, which
  makes the narrative read incorrectly. In
  `console-demakes/llm-transcripts/sep-18-25_agent-1.md` one such recap runs
  from line 383 to line 587 — 204 of the file's 683 lines, about 30% of the
  transcript — under the user's heading. Giving it its own kind of heading
  keeps every line while letting the recap announce itself as a recap.
- **`/compact` invocations**, as the beat that introduces the recap that
  follows.
- **`/clear`**, as a deliberate reset — a chapter break in the narrative.

### Group three — kept unchanged

- Everything the user typed.
- Everything the model wrote as prose.
- Question exchanges, with their answers and notes, per issue #019.

**`/model` is deliberately absent from all three groups.** It passes the test —
it plainly changes the course — but the scaffolding recorded for it is the
wrong source to read, for reasons set out in issue #023, which handles model
changes on its own.

## Suggested Implementation Steps

1. **Name the categories in one place.** Following the project's preference
   for dispatch tables over branching, the classification belongs in a single
   table mapping a recognised envelope shape to its disposition — dropped,
   relabelled, or kept — so that adding a newly observed shape is a table entry
   rather than a new branch buried in the message loop.
2. **Recognise shapes by their markers, not by guessing.** Each kind has an
   unambiguous marker already present in the text: the caveat tag, the
   command-name tag, the compaction opening sentence. Recognition should key
   on those, and anything unrecognised must fall through to being kept — the
   safe direction, since keeping something unwanted is a cosmetic problem and
   dropping something wanted is data loss.
3. **Warn on the unrecognised.** When a message is kept only because nothing
   recognised it, print a line naming the conversation. This is how the next
   new envelope shape gets noticed instead of quietly accumulating, which is
   what happened with every defect in issues #019 and #021.
4. **Give recaps their own heading kind.** A distinct heading, parallel to
   `### User Request N` and `### Assistant Response N`, so the existing
   numbering of real user turns is not disturbed by recaps taking slots in it.
5. **Handle list-shaped content properly.** The user-turn writer should render
   content that arrives as a list of blocks by concatenating its text blocks,
   rather than silently writing nothing. This closes the empty-block defect at
   its cause, independently of whether the notices that trigger it are also
   dropped by the classification.
6. **Do not renumber retroactively.** Dropping envelope traffic will change
   the numbers attached to user requests in any re-derived transcript. That is
   a consequence worth stating out loud before it surprises anyone comparing
   an old transcript to a new one; see issue #024.

## Metadata

- **Priority**: unset — see Open Questions.
- **Complexity**: Medium. The mechanism is simple; the judgement about what
  belongs in a narrative is the hard part, and most of it is unresolved below.
- **Dependencies**: None mechanically. Overlaps #021 and #023 in scope.
- **Impact**: Transcripts read as a design narrative rather than a mixed
  record. User request numbering changes in any re-derived transcript.

## Success Criteria

- No transcript contains a `### User Request` block whose entire body is
  harness boilerplate.
- No transcript contains an empty numbered block.
- Compaction recaps are preserved in full, under a heading that identifies
  them as recaps rather than as user turns.
- An envelope shape the classification does not recognise is kept and reported,
  never silently dropped.
- A session containing no envelope traffic is unchanged except for numbering.

## Open Questions

1. **Do we want to implement this at all?** Every defect here is cosmetic —
   nothing the user said is currently being lost to envelope traffic. The
   argument for doing it is entirely about how the transcripts read as a
   narrative. The argument against is that it means the exporter starts making
   editorial judgements about what belongs in the historical record, which is
   a different kind of program than the faithful dumper it is today.
2. **Does `[Request interrupted by user]` belong in the narrative?** It is not
   something the user *said*, but it is unmistakably something that *changed
   the course* — the model was stopped mid-work. Under the stated test it
   should be kept as a beat. It currently renders as an empty block, so it is
   being lost either way. Keeping it means the transcript records the moments
   the user intervened, which are often the most revealing moments in a design
   record.
3. **Should compaction recaps be relabelled, or left exactly as they are?**
   The instruction was that the summaries are wanted, which settles whether
   they are kept. It does not settle whether the heading above them changes.
   Relabelling is not filtering, but it is still a change that was not asked
   for.
4. **Is the housekeeping list right?** `/usage`, `/config`, `/extra-usage`,
   `/login`, and `/remote-control` are proposed for dropping on the grounds
   that they leave the work where it was. `/config` in particular can change
   the output style, which arguably does change the course.
5. **What happens to a slash command this project itself defines?** The survey
   only covers built-in commands. A project-specific command would carry
   arguments that could matter a great deal, and the classification has no
   entry for that case.
6. **Should dropped traffic vanish entirely, or be summarised?** A single line
   noting that housekeeping occurred preserves the shape of a session — that
   the user paused to check something — without the noise. Vanishing entirely
   is cleaner but makes the transcript claim a continuity the session did not
   have.
7. **Does dropping envelope traffic conflict with the project's append-only
   instincts?** The corpus is treated as a historical record, and this issue
   proposes that the exporter decide parts of that record are not worth
   keeping. The session logs that would justify a later change of mind are
   culled on a schedule, so a dropped category is only recoverable for as long
   as its log survives.
