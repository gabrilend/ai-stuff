**1. Which rule for overlapping words should be built after "blank the whole
word"?**
When one voice's new words land partly on top of a word another voice wrote, the
current default blanks the damaged word entirely. Six other rules are designed:
- **fade the fragments:** keep the leftover letters but dim them.
- **keep the fragments:** leave the leftover letters as they are.
- **refuse the cut:** reject any write that would split a word.
- **push aside:** shift the old word out of the way.
- **blank the sentence:** clear the whole sentence the word belongs to.
- **tell the voice:** a switch that reports the damage back to the voice that
  caused it.

Each rule that gets built has to be tested beside the others. Which one should
come next?

**2. Does the one way in from the internet (the "causeway") need a key, and
encryption?**
The canvas server on kuvalu is the only program reachable from outside. With no
key, anyone who finds the port number can read the canvas. With no HTTPS, the
canvas crosses the internet as plain readable text. A related question: which
port should the router forward?

**3. How many words can a voice change in one turn, and how many whole sentences
can it rewrite?**
These are the change limits the fit check enforces before a voice's canvas is
accepted. Strict limits push voices to edit single words rather than rewrite
sentences. Limits that are too strict mean a voice can never bring in a new
idea.

**4. In distill mode, whose name goes on a change?**
In distill mode, kuvalu reads all three voices' proposals and writes one merged
result. Should each change be credited to kuvalu, or to the voice the idea came
from? Crediting the voice means the distiller also has to report where each
change came from, which is one more thing it can get wrong.

**5. How should the canvas change size?**
Every word sits at a fixed row and column, so shrinking the canvas cuts off
words near the edges, and growing it leaves empty space. The options:
- **(a)** The size is fixed for each run.
- **(b)** The size can change only between runs.
- **(c)** Resizing is allowed during a run, which clears all the marks about who
  wrote what and tells the voices.

**Your HTTP answer runs into two technical catches:**

**1. Where does the browser get the key?** If the page arrives over plain HTTP
with the key written inside it, anyone who can read the traffic gets the key
along with the encrypted canvas. The encryption then protects nothing. So the
key has to reach the browser some other way:
- You type it in once, and the page remembers it.
- It rides in the page address after a `#`, like `http://…/canvas#k3y…`.

**The next five:**

**2. Should the canvas history survive a restart?**
Every canvas a voice sends says which version it was editing, for example "I
started from version 41". kuvalu keeps the old versions so it can compare
against version 41 and see exactly which words that voice changed. Those old
versions live only in RAM, so a reboot wipes them. After a reboot, every voice's
next canvas names a version kuvalu no longer has, and it gets refused. Saving
the history to disk would fix that, at the cost of disk writes on every version.

**3. Which C library and which tools do the three mini-computers have?**
A C library is the base layer every compiled program on a Linux system calls
into, and comes in two common kinds, glibc and musl. A program built against one
usually won't run on the other. The voices' model client uses `curl` to talk to
the llama.cpp servers, and the project copy on each voice is made with `git`. If
either tool is missing, it has to be installed or the plan changes. A survey of
the machines would answer this, and nothing is blocked on you here except
permission to look.

**4. Can rmail be told not to look up its public address or open a port on the
router?**
When rmail starts, it asks an outside website "what's my public address?". It
also asks the router to forward a port to it automatically, using protocols
called UPnP or NAT-PMP. Your network rules only allow outside connections to
language-model providers, so those requests will either be blocked or break the
rules. Is turning those features off acceptable, given you said you'd tune rmail
per setup?

**5. Should kuvalu tell each voice which model server to use?**
Right now each voice keeps its own file listing the model servers it can use.
Alternatively, kuvalu could write "use this server" as one line at the top of
each canvas it sends out. Then switching all three voices would mean changing
one place on kuvalu, instead of three files on three machines. The cost is one
more line in the canvas format.

**6. Where does the tool that builds the project's search index live?**
The voices find relevant code by searching an index: each name in the source
(variable, function, structure) is turned into a list of numbers (an embedding),
and the search finds the names whose numbers are closest to the query. Something
has to build that index. If the builder lives in delta-version, every project
copies it in, since projects don't depend on each other. Should the first copy
be built right here in guide-feature, so the search tool has a real index to
test against?
