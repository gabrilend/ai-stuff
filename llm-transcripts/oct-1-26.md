## Before writing a new issue

1. **Search first, including `issues/completed/`.** Grep the issue tree for
   the feature's nouns, not just the likely title. A completed issue about the
   same machinery is reopened and extended rather than duplicated: history is
   more useful stacked vertically in one file than spread across several.
2. **Pick the phase by what the work builds on**, not by when it is being
   done. Lower numbers are foundations; later issues depend on earlier ones.
3. **Take the number from the tool:** `validate-issues <project> --next
   <phase>`.
   It reads the project's own naming shape (522, 1001, 9-007, A04) and never
   reuses a number that a completed file already holds.
4. **Write the blueprint** with the three sections CLAUDE.md requires, plus
   link fields in the shape the project already uses (look at a neighbour).
   Name related functions, structures and files instead of pasting code.
5. **Check it:** `validate-issues <project> --file <new-issue>`, and fix what it
   reports on the new file. If the new issue blocks or is blocked by others,
   add the matching line to the other side too.

## While working

- Keep **Current Behavior** true. It is the only section that changes while
  an issue is in progress; rewrite it in place rather than appending a log.
- A question that surfaces is written into the issue (an "Open questions"
  section) and then asked. An issue with an unanswered question is in
  progress, not done.
- Anything discovered that changes another issue's assumptions is written into
  that issue now, not at completion.

## Splitting into sub-issues

Split when an issue holds work streams that could be built, tested or reviewed
separately, or when it cannot be finished in one sitting. Do not split an issue
that is already one mechanism. When splitting, produce and then write out:

1. **A table** — `| ID | Name | Dependencies | Description |`, where ID is the
   parent number plus a lower-case letter (103a, 103b), Name is dash-separated
   lower-case words, Dependencies is "None" or sibling IDs.
2. **The rationale** — the distinct work streams, why one issue cannot hold
   them, what splitting buys.
3. **The execution order** — a small dependency graph, e.g.
   `103a (foundation) → 103b (needs 103a) → 103c (parallel with 103b)`.

Each row becomes a file `{parent}{letter}-{name}.md` with the three sections.
The parent keeps its blueprint and gains a short list of its sub-issues; the
analysis itself is not appended to the parent (that would be worklog, not
blueprint). Run `validate-issues` afterwards: it reports orphaned sub-issues
and one-sided links.

## Completing an issue

An issue is complete only when nothing in it is deferred and no open question
is unanswered. Then, in this order:

1. **Run the project's tests.** A fixed bug gets a test that would have caught
   it.
2. **Rewrite the issue as the blueprint of what was built**: Current Behavior
   states the built system; steps name the real functions and files; decisions
   not taken are stated with their reason. Poetry the owner wrote during the
   work goes into the issue verbatim.
3. **Move it** into `issues/completed/` (`git mv`, so the history follows).
4. **Update `issues/phase-<N>-progress.md`** for that phase. Take counts from
   `progress-dashboard.lua <project> -m`, or better, name the command instead
   of copying numbers that will go stale.
5. **Update related issues** whose Current Behavior or assumptions changed.
6. **Run `validate-issues <project>`** and fix new findings that the change
   caused. Findings older than the change are reported to the owner, not
   silently fixed in passing.
7. **Commit** as below.

## Committing

The rule (CLAUDE.md): a commit carries exactly the lines this session wrote —
never another session's work, even if it sits in the same file — and every
changed transcript of the commit's projects rides along — the session's own
project folder and the projects of the files it commits — this
conversation's and any other's left behind (a session that committed, talked
on and quit), so each project's story in git stays whole.

Commit small and often: each piece as soon as it is done and checked, not a
pile at the end.

1. Optionally preview: `stage-own-changes <repo>` lists what would be taken
   and what left out, and writes nothing.
2. Commit: `commit-own-changes <repo> -F -` with the message on standard
   input. It builds the commit on a private staging list from this session's
   own lines (the edit ledger the edit hook keeps) plus those transcripts, and
   never touches the shared staging area, so nothing another
   session has staged can ride along. Plain `git commit` is refused by the
   commit gate.
3. Message style: say what the software now does, in plain English and by
   mechanism or analogy; mention any extra changes and why. No function names.

**When it stops or leaves something out.**

- **A tangled ("mixed") block** means another session changed lines right
  next to or on top of yours. Nothing is committed. Tell the owner which file
  and line; decide together what that region should say. `--leave-mixed`
  commits your other blocks meanwhile.
- **Lines that are yours but were written by a route the ledger could not see**
  (a script you ran, a generator, `sed`, a rename): record them with
  `claim-own-change <file>` and say so in the commit message.
- **Nothing to commit, but the work is there**: an earlier session wrote it
  and ended, or the machine rebooted and emptied the ledgers. Look first with
  `adopt-left-behind-changes <repo> --dry-run -- <path>...`, then adopt and
  commit one batch at a time with `commit-own-changes <repo> -F - --
  <path>...`. Lines reported as **held** belong to another session. Take them
  (`--from <session>`) only if that session has finished, and ask the owner
  if unsure. Say in the commit message that the work was adopted and from

**On the clean room:** no, pushing away doesn't break it. A classic clean room
has three groups:
- one describes the original in words;
- a second builds only from that description, never seeing the original;
- a third compares the result to the original and **sends back anything too
  close**.

Your similarity scores are that third group. A filter that can only say "too
close, redo this region" can't move the output toward the original. It only
removes nearness. The original does shape the result, but only through what it
ruled out, and that is the point of the check.

One detail decides whether this stays true. When a region is regenerated, do you
keep the **first** version that passes, or do you generate several and keep the
passing one that **scores closest**? The first is pure avoidance. The second
quietly steers toward the original, because it picks whatever is nearest the
line from the allowed side. That would make it the bit-leak I described. The
same goes for the threshold: if it's ever loosened when results look "too
different", the original is steering.

### Assistant Response 15

I've recorded both answers in the redaction issue.

**Picking by what users like** keeps the legal guarantee, because nothing past
the distinctiveness line ever ships. In information terms, though, the people
choosing are the channel: most of them have seen Warcraft III, so "looks right"
carries some of the original through their memory. You don't have to settle that
by argument; you can measure it. Log the similarity score of every version
people chose and every version they passed over. Then compare:
- **No difference between the two groups:** taste was independent of the
  original, and that's strong evidence for the clean-room claim.
- **The chosen ones sit nearer the line:** the crowd is steering toward the
  original, and you can say how much.

Either result is honest, publishable data. That seems like the strongest
position for the legal case: neither denying the steering nor ignoring it, but
measuring it.

**On selling training data:** I think it's a good idea, with four things to
settle.

1. **What anchors "reasonable"?** Patent law already has a term for exactly
   this: **FRAND**, "fair, reasonable and non-discriminatory". It's what
   standards bodies require of patent holders whose patents are essential to a
   standard, and courts have spent years working out what it means. The
   "non-discriminatory" part matters most here: the same price for everyone who
   asks, so a seller can't price out one particular requester. You'd be
   borrowing a term that already has case law instead of inventing one.
2. **What is a fraction measured in?** Item count is simple, and so are bytes.
   The share of influence each item had on the weights would be the fairest, but
   nobody can compute that reliably yet. I'd start with count or bytes and let
   the price per item vary.
3. **Other people's personal information can't be sold.** The fediverse posts
   are the case here. Whatever is sold has to be the redacted version, so the
   redaction rule comes first.
4. **Data the trainer doesn't own.** You can't sell someone else's poems. For
   that data, I'd require the trainer to list where it came from instead: its
   provenance.

There's also a side effect I like. The people whose writing and art went into a
model become sellers in a small market. The current setup offers them nothing at
all.

Question back: **should the price be set by the person who made the data, or by
the person who trained on it?** They're often different people, and FRAND only
says the price must be fair, not who sets it.

### Assistant Response 16

No, it's not too complicated. As license terms, it comes down to three numbers
and a list per dataset:
- a price for the whole set;
- the unit a fraction is measured in;
- a royalty rate for each piece (M dollars per N dollars sold);
- the provenance list, which says who made each piece.

Everything else is mechanism: tools that carry out those terms, and they don't
need to be written into the license. I've recorded your terms in the redaction
issue, marked to move into the RGPL's own documents later.

Two pieces of mechanism keep the fairness you're after from leaking away:

1. **Repeat purchases must not draw duplicates.** If a buyer's second 10% is
   drawn independently of their first, they get overlap. After ten purchases of
   10%, they'd hold only about 65% of the set, having paid the full price. The
   poorer buyer pays more for less, which is exactly what you're trying to
   prevent. The fix: each later purchase draws only from items that buyer
   doesn't hold yet.
2. **The random draw has to be checkable.** Otherwise "random" can quietly mean
   "the boring pictures". The standard trick is commit-then-reveal:
   - before any sale, the seller publishes a fingerprint (hash) of the full item
     list;
   - the buyer chooses the random seed;
   - anyone can then re-run the draw and confirm the seller handed over exactly
     what the seed picked from the list they committed to.

One consequence to say out loud. "Pay the creators when the dataset is
assembled" means a model trained on scraped data, millions of creators, none of
them asked, can't meet these terms. That rules out most of how models are built
today. If that's the intent, it's a strong position, and the license should say
so plainly rather than leave readers to discover it.

**Routing royalties** through the provenance list works as long as each entry
can carry a way to pay its creator. For creators who can't be reached, the
royalty is owed but has nowhere to go. It needs a place to wait: a published,
append-only ledger of what's owed to whom, which the creator can claim from
later.

Question back: **if someone buys the dataset and resells it, do the royalties
follow it?** If they don't, the first buyer can resell it royalty-free, cut the
creators out, and undercut the original seller. If they do, every reseller takes
on the payment duty, so the provenance list becomes a debt that travels with the
data.
