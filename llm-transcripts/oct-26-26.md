## Question 1: other places names get lost
I looked through your scripts folder for everything that reads git's file lists.
Four places read the quoted names. The fifth, the commit-your-own-lines tool,
already uses `-z` and is safe.

| Where | What a non-ASCII name does there |
|---|---|
| **carry-back script**, the step that clears files blocking an incoming merge | It checks whether the quoted name exists on disk, finds nothing, and skips the file without a word. A blocking file is left in place, so the merge can fail later for no visible reason. **This is the worst one.** |
| **Story page's commit-history reader** (transcript site) | It matches each commit's files against the transcripts folder name. A quoted name starts with `"`, so it never matches. That's harmless while transcript names are plain dates. |

## Question 2: sealing the old pages

Git commit hashes already protect the history itself. Each commit's ID is a
checksum of the commit's files, its message and its parent's ID. Changing
anything in an old commit changes its ID and the ID of every commit after it. So
the ledger only needs to seal the pages, not the history.

Proposed mechanism:
- **A ledger file** sits beside the site, with one line per by-hand page: the
  commit ID, the page's checksum and the date it was sealed. Lines are only ever
  added, never edited.
- **Every build** walks the ledger and stops with an explanation on either of
  two faults:
  - **A page's checksum differs from its sealed line.** The message names the
    page and both checksums. It says the page was edited after sealing, or
    rebuilt by a changed builder.
  - **A sealed commit ID is no longer in the history.** The message says the
    history was rewritten, for example by a rebase or an amended old commit, and
    names the commit.
- **New by-hand commits** get built once, and then a line is added to the
  ledger. Old pages are never rebuilt, so the "fatal" messages about ancient
  commits stop as well.

One gap needs your answer: **re-sealing on purpose.** The fix for files with
non-ASCII names should add missing lines to some old pages. Their checksums will
then change, and the check above would stop the build. My recommendation is a
separate re-seal command you run by hand. It rebuilds the pages and adds new
ledger lines with a reason you type, such as "added the lines lost to quoted
names". The old lines stay, so the ledger shows every time a sealed page was
changed and why.

Before I write the issue file and start, tell me in your own words: what would
count as tampering for you? Is it someone editing a page file, someone rewriting
an old commit, or the builder changing what it writes? The mechanism above
catches all three, but it stops the build with the same error for each. You may
want them treated differently.

Once you answer, should I fix all of these? That means the `-z` fix in the page
builder, the same fix in the carry-back script and the story-page readers, and
the sealed cache, each with tests.
