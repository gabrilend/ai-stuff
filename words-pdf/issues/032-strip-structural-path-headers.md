# Issue 032: Strip Structural Path Headers From The Corpus

## Current Behavior

Each block in `input/compiled.txt` is prefixed with a structural header
line naming the source file it came from, e.g.:

```
 -> file: fediverse/1234.txt
```

`load_file` keeps every line that is not the 80-dash delimiter, and
`normalize_poem_spacing` only trims leading blank lines — neither removes
this header. So the header survives into:

1. **The embedding.** `themes-v2/load-poem-embeddings.lua` embeds the
   normalized poem text, header included. 6000 of 7807 blocks live under
   `fediverse/`, so the literal token "fediverse" (plus "file", "txt",
   and the path number) is injected into ~77% of all poem vectors as pure
   metadata. This is structural noise read as content: "fediverse" and
   "https" rank as *top TF-IDF words* of the largest cluster, the HDBSCAN
   clusters collapse toward online/social semantics, and the
   cluster→generator matcher hands ~42% of poems to the single
   `online_communities` motif (a hub vector close to everything), leaving
   12 of 21 Tier 2 generators dormant. The LLM namer also keeps emitting
   `fediverse_*` cluster names because the word is everywhere.

2. **The rendered PDF.** The same header text is drawn inside each poem
   box, printing a source file path the reader never wanted to see.

`detect_poem_type` *relies* on the `fediverse/` path to choose between the
`fediverse_with_cw` / `fediverse_no_cw` / `messages_notes` formatting
branches, so the header cannot simply be removed before classification.

A second, related contaminant surfaced after the header strip landed: some
blocks are image-only / file-only posts whose entire body is an attachment
filename or bare timestamp (e.g. `screenshot_20250414_154457.jpg`,
`temp1239479072698940656.PDF`, `cameron-king-resume.txt`,
`20250414_154457`). These ~300 digit-soup lines cluster together purely on
their filename tokens, producing junk micro-clusters. Same class of bug,
same fix: strip them too.

## Intended Behavior

The path header is corpus structure, not poem content. After
`detect_poem_type` has used it to classify the block, the header line is
dropped so that neither the embedding nor the rendered page ever sees it.
Embeddings then reflect what each post actually says; clustering and the
generator distribution are measured on honest text.

This is the data-hygiene fix that sits *upstream* of the entire 02x theme
system (029 discovery, 030 registry, 031 Tier 2 motifs). Those issues are
implemented and were faithfully clustering/matching whatever text they
were handed — they were handed contaminated text.

## Suggested Implementation Steps

1. In `normalize_poem_spacing`, immediately after the `detect_poem_type`
   call (which still needs the header), filter the working poem to drop
   structural lines, then run the existing per-type branch logic on the
   filtered lines. Two patterns count as structural: the source header
   (`^%s*%-+>%s*file:`) and a whole-line attachment filename/timestamp (a
   single space-free token ending in a known media/doc extension, or a
   bare `YYYYMMDD_HHMMSS` stamp).
2. Apply the identical change to BOTH copies of the function: the render
   copy in `compile-pdf-ai.lua` and the verbatim embedding copy in
   `themes-v2/load-poem-embeddings.lua`. They must stay in sync or the
   embedding cache key diverges from the rendered text.
3. Rebuild the taxonomy (`./run themes-rebuild`). Changing the embedded
   text changes every affected poem's cache key, so this re-embeds the
   corpus once — expected and correct; the old cached vectors were of
   contaminated text.
4. Re-print the theme/generator selection statistics and compare against
   the pre-fix run. The expectation: clusters differentiate by real topic,
   `online_communities` stops being a 42% sink, and previously-dormant
   Tier 2 motifs start getting selected.

## Follow-up (separate, only if still needed after the rebuild)

If the generator distribution is *still* concentrated on honest text, the
matcher itself (`find_best_generator` in `themes-v2/name-clusters.lua`) is
a hub-vector problem: raw cosine always favors a generator whose style
description sits near everything. The fix there is to gather the full
cluster × generator similarity matrix, normalize per generator (compare
*distinctive* affinity, not raw closeness), and assign by the strongest
normalized matches — prioritizing great matches rather than penalizing
reused generators. Deferred until the data fix is measured.
