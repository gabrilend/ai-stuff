**The algorithm**


The terminal is a 2D grid of character cells. The cursor sits at one cell. ANSI
escape codes can move it (`\27[NA` = up N lines), clear from cursor to end of
screen (`\27[J`), and set foreground color (`\27[38;5;Nm` for 256-color). That's
the whole toolkit.


We want a fixed region near the bottom of the scrollback that re-paints itself
each page. Trick is: pages don't all produce the same number of status lines (a
page with 17 poems prints more than a page with 4). So we use a **high-water
mark**:


```

state:

max_region_height = 0 -- grows monotonically

buffer = {} -- this page's lines, collected by log()

pages_done = 0

tty = io.open("/dev/tty", "w") -- nil if non-interactive

log = io.open(os.getenv("LOG_FILE"), "a")

```


Per page:


```

start_page(n):

if tty and pages_done > 0:

tty:write("\27[" .. max_region_height .. "A") -- jump back to anchor

tty:write("\27[J") -- erase old frame

buffer = {}

push the colored progress bar onto buffer -- bar is line 1 of the frame


log(text):

append text to buffer

log:write(text .. "\n") -- always log, even if no tty


end_page():

if tty:

for each line in buffer: tty:write(line .. "\n")

used = #buffer

if used > max_region_height:

max_region_height = used -- grow the anchor

else:

for i = used+1, max_region_height:

tty:write("\n") -- pad to keep anchor stable

else:

for each line in buffer: print(line) -- non-interactive: just scroll

pages_done += 1

```


Key invariant: after `end_page()` returns, the cursor is **exactly
`max_region_height` lines below the anchor**, every time. That's what makes
`\27[<max_region_height>A` work as a "jump back to anchor" on the next
iteration. The padding lines exist solely to enforce this invariant on pages
that didn't use the full height.


When `max_region_height` grows mid-run (the first time you hit a page with more
lines than seen before), the anchor shifts down once and stays there. You'll see
one "lurch" in the UI at that moment, then it stays put.


**The color gradient** is computed once per page from `page_num / total_pages`, mapped through a dispatch table:


```

{0.0, 17}, -- dark blue

{0.2, 93}, -- purple

{0.4, 51}, -- cyan

{0.6, 226}, -- yellow

{0.8, 46}, -- green

```


Each filled `█` gets wrapped in `\27[38;5;<code>m...\27[0m`; the empty `░`
chars and the surrounding "Processing page N/M" text stay default (which on most
terminals reads as white-on-black). Result: the filled portion of the bar starts
dark blue, fades through the spectrum, ends green.


**Log file always gets the plain text** — no ANSI codes, no redraws, just every line in order. So `cat tmp/logs/run-*.log` after the run reads like the current scrolling output does today.


**Non-interactive fallback** (no `/dev/tty`, e.g. piped to a file or running under CI): `tty` is `nil`, the redraw branches skip, every line just `print`s. You get today's behavior, unchanged.

nearest-centroid assignment**: HDBSCAN finds the dense "core" structure as usual

## 1. Building the theme catalog — what `./run themes-rebuild` actually does


This phase happens **once per content change** (or generator-registry change).
It produces one artifact: `themes/derived-taxonomy.lua`. Inside the script there
are four sequential steps:


**Step 1 — collect poem vectors.** `load-poem-embeddings.lua` reads `tmp/compiled-cleaned.txt`, splits on the 80-dash delimiters into ~7800 individual poems, and for each one asks the embedding server (nomic-embed-text on the GPU box) for its 768-dim vector. The embedding server's responses are cached on disk, so the second time you run this it's basically instant. Output: one packed binary file of 7800 × 768 float32 numbers, plus a parallel text-lookup file.


**Step 2 — find the natural clusters.** `hdbscan.lua` runs HDBSCAN on those vectors. Conceptually it asks: "in 768-dimensional space, which poems are near which other poems?" It finds the dense regions and labels them clusters; everything not in a dense region is "noise." Then a post-hoc pass reassigns every noise poem to its nearest cluster centroid, so every poem ends up belonging somewhere (100% coverage). It writes the cluster IDs, the core centroid of each cluster, and the membership lists.


**Step 3 — extract distinctive vocabulary.** `tfidf.lua` looks at each cluster's poems and finds the words that are common within the cluster but rare across the corpus as a whole. These are the cluster's "fingerprint" words — `capitalism, fediverse, mentioned` for one cluster, `food, ramen, recipe` for another, etc.


**Step 4 — name and assign generators.** `name-clusters.lua` does three things per cluster:


- **Naming**: builds a prompt for Qwen3 with the cluster's top TF-IDF words + 3 representative poem excerpts. The prompt includes alternating good/bad few-shot examples to teach the format. Qwen3 returns 5 candidate snake_case names. Each candidate is embedded via nomic; the one whose embedding is closest to the cluster's centroid wins (the cluster picks the name that best represents its own semantic position).

- **Generator mapping**: every generator in `themes/generators.lua` has a `style_description` like "Explosive radial rays bursting from a center point in red, suggesting uprising, revolt, militant collective action." Each style_description gets embedded. The cluster's centroid is compared to each generator's style embedding; whichever has the highest cosine similarity wins. So if a cluster centroid lives in the same neighborhood as the "circuit" generator's style description, the cluster gets assigned the `circuit` generator.

- **Parameter axis pre-computation**: that chosen generator has declared parameters with `low_words` and `high_words` (e.g. `circuit.trace_count.low_words = "simple sparse atomic basic"`, `high_words = "complex dense intricate distributed"`). Each pair gets embedded; `axis_vector = normalize(embed(high) - embed(low))` is computed. This axis is a 768-dim direction in embedding space pointing from "low end of the parameter" to "high end."


The output `themes/derived-taxonomy.lua` lists every cluster with: a name, its
centroid, its assigned tier1 generator name, and the parameter axes for that
generator. That file is everything the PDF runtime needs to know.

## 2. Page rendering at runtime — what `./run` does with the catalog


At startup `compile-pdf-ai.lua` reads `derived-taxonomy.lua` into a `THEMES`
table. Then it does one big pre-pass before the page loop:


**Per-page percentile pass.** For every page in the book, concatenate its poem text and embed it. Then for every cluster's parameter axes, project the page's embedding onto each axis (a dot product). After every page is projected, rank-sort by projection score and convert each page's rank to a percentile in [0, 1]. Result: `PAGE_PERCENTILES[page][theme][param] = 0.73` (meaning "this page is at the 73rd percentile of the corpus on this parameter's axis").


Then the page loop runs. For each page:


**a) Which theme?** `analyze_page_themes` embeds the page and finds the closest cluster centroid by cosine similarity. The cluster's name is the page's theme.


**b) Should we even draw page art?** `generate_page_art` runs the Issue 028 geometry check: `calculate_art_spaces` partitions the page into "outside regions" (bottom strip, left outer margin, right outer margin, center gap between columns). Each region's area is measured against the page area; regions ≥ 8% of the page qualify as worth drawing into. If no qualifying region exists, the page gets no Tier 1 art. (This is the part you fixed earlier — the gate is per-region area, not global page fullness.)


**c) Which generator and what params?** For each qualifying region, `draw_theme_art_in_spaces` looks up the theme's metadata in `THEMES`:

- `THEMES[theme].tier1_generator` → the generator name (e.g. `"circuit"`)

- `generators.tier1["circuit"].draw` → the actual draw function

- `PAGE_PERCENTILES[page][theme]` → the parameter values for this page (e.g. `{trace_count=0.65, segments_per_trace=0.42}`)


**d) The actual drawing.** The generator's draw function receives the rectangle (one of the outside regions) and the params table. Each generator has a visual vocabulary: `circuit` draws Manhattan-geometry traces with junction nodes; `lightning` draws jagged bolts top-to-bottom; `spiral` draws concentric arcs. The params table tweaks quantitative knobs declared by the generator: how many traces, how jagged, how big the gold center. Internally, the generator does `actual_value = min + percentile * (max - min)`, then uses that for its loop count or magnitude.
