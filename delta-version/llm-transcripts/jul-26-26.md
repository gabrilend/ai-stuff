## Question 2: the `**` and `-` line wrapping


The wrapping logic itself is fine. I fed adversarial input through the
exporter's own `wrap_text` — bold openers wrap, bullets wrap with a correct
hanging indent, nested bullets keep their indent. The real defect is that **a
blank line is injected after every single line**:


```

=== two adjacent bullets

 1| - first bullet is short

 2| <BLANK>          ← phantom

 3| - second bullet is short

 4| <BLANK>          ← phantom

```


Root cause is one character in `conversation-parser.lua:64`:


```lua

for line in text:gmatch("[^\n]*") do

```


`[^\n]*` can match the empty string. Lua's `gmatch` yields that empty match at
every newline position, then advances one byte — so you get `"line"`, `""`,
`"line"`, `""`… and the blank-line branch at line 72 faithfully writes each
phantom out.


`★ Insight
─────────────────────────────────────`

This is the single most common Lua pattern bug: any `gmatch` quantifier that can
match zero characters (`*`, `-`, `?`) produces a phantom empty match between
every real one. The safe line-splitting idiom is `for line in (text ..
"\n"):gmatch("(.-)\n")` — the appended newline guarantees a terminator for the
last line, and `(.-)\n` cannot match without consuming a `\n`, so there's no
zero-width match to repeat.


Why it *looks* like a `**`/`-` problem specifically: those are the two
constructs where Markdown cares about line adjacency. Two adjacent `- ` items
separated by a blank line become a *loose* list (each item gets wrapped in
`<p>`, rendering with vertical gaps), and two adjacent `**Label:**` lines become
two separate paragraphs instead of one block. Plain prose that got re-wrapped
anyway hides the damage completely.

`─────────────────────────────────────────────────`


You can see it in your committed output —
`llm-transcripts/jul-25-26-through-jul-26-26.md:164-166` has a doubled blank
after `**[Asked the user]**`, and lines 170-186 are a bullet list with a blank
between every item.


**There's a second, independent defect in the same function:** the width test
counts *bytes*, not characters. `#line <= width` at line 74 and `#current + 1 +
#word <= width` at line 53 both use `#`, and an em-dash is 3 bytes in UTF-8.
Measured result from the probe:


```

- an em-dash heavy line — with — several — em — dashes — that —   [bytes=75 chars=63]

```


That line broke at 63 visible columns because seven em-dashes ate 14 phantom
columns. Since you're wrapping model prose — which is dense with `—` —
most lines come out short with a ragged right margin. It hits `- ` bullets
hardest, because the AskUserQuestion renderer formats every option as `- label
— description` (`conversation-parser.lua:193`), guaranteeing an em-dash in
each one.


## The fixes


Three changes, all small:


1. **`conversation-parser.lua:64`** — swap the split idiom to `(text ..

2. **`conversation-parser.lua:53,74`** — measure width in codepoints.
