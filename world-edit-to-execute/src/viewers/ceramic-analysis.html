Ceramic Frame Budget

The task

A real-time strategy renderer redraws the battlefield sixty times a second, so each frame has 16.67 ms for everything: game rules, animation, and drawing. One of the heaviest per-frame jobs is posing skeletons. Every unit on screen is a model hung on a chain of bones, and each frame every bone's position has to be worked out again from the animation's clock: a small rotation, then a 4×4 matrix product onto its parent bone, down the chain. Here each unit has 30 bones, so its pose is 30 matrices, 1920 bytes.

The work for one unit is small (about on one core) and every unit is independent of every other, which makes it the textbook job to spread across cores. The question this study answers is whether the ceramic engine (soramech, where a program is plain C functions wired together and a function runs as soon as all its inputs have arrived) can do that job inside a frame, and what shape the work has to take for it to pay.

Why not the graphics card? A shipping engine would often do this there: the graphics card is built for exactly this arithmetic, thousands of matrix products at once. Here the skeleton stands in for any per-frame work that stays on the processor (game rules, pathfinding, fog of war, deciding what is visible), because it is real work of a realistic size with an answer that can be checked. The question is how well the engine spreads a frame's work across cores, not where skeletons belong.

Why is a pose 1920 bytes? A skeleton is stored compactly: each bone's offset from its parent as a position (3 numbers) and a rotation (a quaternion, 4 numbers), about 28 bytes, and the bone's number is just its place in the list. But the answer a renderer needs is each bone's final placement in the model, every parent's turn already folded in, as a 4×4 matrix the graphics card applies to the bone's vertices: 16 numbers × 4 bytes = 64 bytes, × 30 bones = 1920 bytes. Sending quaternions instead would shrink it to about 840 bytes and move the folding onto the graphics card.

Every approach below computes exactly the same poses, checked by checksum against the one-thread loop.

Five approaches

Each keeps its colour on every chart below.

One threadthe plain loop

A for loop over every unit on a single core. No parallelism at all: this is what the work itself costs, and the yardstick for every speed-up.

Hand-written thread loopfixed slices, one per thread

One thread per hardware thread, created once. Each frame, every thread poses its own fixed, equal share of the units (with 12 threads, about 171 each), then all of them meet at a barrier. It is the classic hand-built answer and the shape of this project's existing render thread pool. Equal shares don't finish at equal times, though: two threads share each physical core and run at roughly half speed, and the operating system interrupts threads at random, so the frame ends when the slowest thread finishes.

Hand-written loop, shared counterthe same threads, no fixed slices

The same threads, but instead of a fixed share each one repeatedly takes the next run of units (32 at a time, or as many as the chart says) by adding to one shared counter, until the units run out. A thread that is slowed simply takes fewer runs. It is the hand-written equal of the ceramic engine's chunked tasks, and shows how much of the engine's advantage is just this self-balancing.

Ceramic, one unit per taskthe engine, finest grain

The renderer's main thread hands the engine one small request per unit (“pose unit 812 at time t”). Each request becomes a task handed in to the engine's task queue; whichever worker is free takes it, runs the pose function, and the 2 KB pose is copied back into the renderer's array. The most natural way to write it, and the most hand-ins: one per unit, every frame.

Ceramic, chunkedthe engine, one task per group of units

The same engine and the same function, but each request covers a run of units (16, 32 or 64 of them), so the renderer hands a few dozen tasks per frame in to the task queue instead of thousands. Free workers still take whichever task is next, so the load balances itself.

What one ceramic task goes through

renderer hands in a request→the task is built (inputs copied)→handed in to the task queue (one lock)→a free worker takes it and runs the box→the answer is copied into the renderer's array
the task queue
the engine's one list of tasks ready to run, shared by all its workers. Whichever worker is free takes the oldest.
handing in to the task queue
the renderer's thread delivering a request, which the engine turns into a task and adds to the task queue. It is serial: one thread hands every task in, one at a time. Drawn in amber on every chart.
the queue lock
the stock engine guards the task queue with one lock. Handing a task in to the task queue takes the lock; so does every worker taking a task out of it.
landing
an answer being copied into the renderer's array. The frame is done when the last answer has landed.
