Lockless Task Queue

Why

The first report, Ceramic Frame Budget, measured the stock engine doing a renderer's per-frame work. Where the renderer hands in thousands of small tasks per frame, one at a time, almost all of the frame goes to handing them in to the task queue:

renderer hands in a request→task built→the task queue's one mutex: taken by every hand-in and every take-out→wake every sleeping worker

The design

The engine's input ports already solve this problem for values. Each port slot moves through four states, and the code beside them says “counted after it is published, never before”. The task queue becomes a ring of such slots, each carrying a sequence number with the ring's lap folded in, so that a position-addressed ring can tell this lap's empty slot from the last lap's. Positions are 64-bit and only count up.

Handing n tasks in to the task queue

  1. Read tail, then head. If tail + n − head is more than the ring holds, there is no room (see a full ring).
  2. Claim positions tail … tail + n − 1 with one compare-and-swap on tail; if another hand-in moved it first, read again and retry.
  3. For each claimed position: if the slot still says “ready” from one lap ago, a worker has already claimed it (step 1 saw head move past it) and is two stores from emptying it, so wait out those nanoseconds. Write the task pointer, then publish: sequence ← pos + 1.
  4. Wake sleepers: only if any are asleep, and only as many as tasks were handed in.

Taking a task out

  1. Read head and that slot's sequence.
  2. Says ready (pos + 1): claim it with a compare-and-swap on head, read the task, set the sequence to pos + capacity.
  3. Says less: empty, or reserved and not yet published; nothing to take.
  4. Says more: another worker took it meanwhile; read head again.

Sleeping without losing a wake-up

A worker with nothing to take locks the mutex, raises sleeping, then looks at the ring again. A hand-in raises tail, then reads sleeping. All four operations are sequentially consistent, so one raise comes first in the single order everyone agrees on: either the worker sees the task and doesn't sleep, or the hand-in sees the sleeper and signals it — and the worker holds the mutex from raising sleeping until it is waiting, so the signal can't arrive before it listens. Completion is decided exactly as before, by the last worker to go to sleep.

batched hand-in
a whole frame of requests handed in to the task queue in one call: the positions for all of them are claimed with one compare-and-swap, then filled and published in order, and sleeping workers are woken once. Workers start on the first task while the last is still being written.
waking
the copy wakes a sleeping worker only when one is asleep, and only as many as there are new tasks; the stock engine woke every sleeper on every hand-in.
spinning
an idle worker looks at the ring again a thousand times (a few microseconds) before it sleeps. A worker still looking when the next task arrives just takes it, and nobody has to be woken. It keeps that core busy, which can slow the other thread sharing it.
a full ring
the ring doesn't grow. A thread outside the engine (the renderer) waits for room; a worker, which must never wait, runs the task itself.
landing
the count of collected answers now rises after each answer is copied in, so the renderer can trust it with no workaround wait.

What it costs

P1, G9

The full-ring rule bends two guarantees.

The ring doesn't grow. With no room, a thread outside the pool waits; a worker, which must never wait, runs the task itself. Guarantee P1 says in its cost column that a full ring doubles “rather than making the pusher run a task”, and G9 says every box runs on a worker that picked up a task for it. A chain of rings — link a larger ring when one fills, drain the old one, retire it through the scrapyard once no worker's epoch can be inside it — would keep both, at one more branch on the take-out path.

P2, P3

The ring never moves, and a task run in place overtakes the queue.

P2 (“the ring's storage can move with nothing dangling”) no longer applies as written; first-in, first-out (P3) holds except for the task a worker runs itself when the ring is full.

cores

Spinning costs a core.

A spinning worker occupies its core, and with two threads per core it slows its sibling: chunked frames ran a few percent slower with spinning on. Off by default; it suits a steady stream of hand-ins.

contention

A compare-and-swap on tail can be contended too.

Many threads handing in at once retry against each other — no lock and no sleep, but not free. Batching answers it as well: one compare-and-swap per batch.

memory

Slots are sixteen bytes and allocated up front.

Neighbouring slots share a cache line, so a hand-in and a take-out on adjacent slots touch one line (padding to 64 bytes would cost four times the memory; not measured). The ring's 65536 slots, one megabyte, are allocated and numbered at creation; the stock queue started at eight entries.

fix

The landing counter is a fix, not a choice.

Counting collected answers after they are copied in should be adopted whatever happens to the queue.
