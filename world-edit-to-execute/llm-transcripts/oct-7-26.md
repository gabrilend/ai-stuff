## Before writing a new issue

1. **Search first, including `issues/completed/`.** Grep the issue tree for
   the feature's nouns, not just the likely title. A completed issue about the
   same machinery is reopened and extended rather than duplicated: history is
   more useful stacked vertically in one file than spread across several.
2. **Pick the phase by what the work builds on**, not by when it is being
   done. Lower numbers are foundations; later issues depend on earlier ones.
3. **Take the number from the tool:** `validate-issues <project> --next
   <phase>`.
   It reads the project's own naming shape (522, 1001, 9-007, A04) and never
   reuses a number that a completed file already holds.
4. **Write the blueprint** with the three sections CLAUDE.md requires, plus
   link fields in the shape the project already uses (look at a neighbour).
   Name related functions, structures and files instead of pasting code.
5. **Check it:** `validate-issues <project> --file <new-issue>`, and fix what it
   reports on the new file. If the new issue blocks or is blocked by others,
   add the matching line to the other side too.

## Committing

The rule (CLAUDE.md): a commit carries exactly the lines this session wrote —
never another session's work, even if it sits in the same file — and every
changed transcript of the commit's projects rides along — the session's own
project folder and the projects of the files it commits — this
conversation's and any other's left behind (a session that committed, talked
on and quit), so each project's story in git stays whole.

Commit small and often: each piece as soon as it is done and checked, not a
pile at the end.

1. Optionally preview: `stage-own-changes <repo>` lists what would be taken
   and what left out, and writes nothing.
2. Commit: `commit-own-changes <repo> -F -` with the message on standard
   input. It builds the commit on a private staging list from this session's
   own lines (the edit ledger the edit hook keeps) plus those transcripts, and
   never touches the shared staging area, so nothing another
   session has staged can ride along. Plain `git commit` is refused by the
   commit gate.
3. Message style: say what the software now does, in plain English and by
   mechanism or analogy; mention any extra changes and why. No function names.

**When it stops or leaves something out.**

- **A tangled ("mixed") block** means another session changed lines right
  next to or on top of yours. Nothing is committed. Tell the owner which file
  and line; decide together what that region should say. `--leave-mixed`
  commits your other blocks meanwhile.
- **Lines that are yours but were written by a route the ledger could not see**

  `claim-own-change <file>` and say so in the commit message.
- **Nothing to commit, but the work is there**: an earlier session wrote it

## Threading: it isn't single-threaded, but nearly

The W client runs two threads:

- **The main thread** does input, each frame's simulation, Lua, and every call
  to the graphics card.
- **One read-ahead thread** reads the next ground tiles out of the archives and
  prepares them, so the main thread only has to upload them.

So on every frame, all of the per-frame work happens on one core. That includes
posing every animated model's bones and stepping every particle emitter
(`042-doodads.c`, around lines 899–942). In the WoW world, with a few dozen
figures in view, that's survivable. A WC3 map with 300 units, each posed from
its own skeleton every frame, is exactly the batch work your rules say must
never run on one thread.

There is one fixed limit. An OpenGL context belongs to a single thread, so only
one thread can send commands to the graphics card. Everything before that point
can be spread across cores: posing, particles, deciding what's in view,
preparing ground. The main thread then just hands the finished results to the
card. This project's ceramic engine (a task graph over a worker pool) is built
for exactly that shape.

My question back to you: where do you see the line between "work a worker does"
and "work the main thread does"? Here's one way to frame it. A unit's pose for

jobs that don't touch each other. A particle that collides with the ground needs
to read the ground, which the read-ahead thread may be replacing at that same
moment. What would you do about that second case?

## The ceramic shape (W client issue 110)

Every part of the client's work becomes a station that runs on whichever worker
is free once its inputs arrive. That covers loading, decoding, posing,
particles, working out what's in view, the player's own movement, and Lua. The
only threads that aren't workers are render threads, one per OpenGL context.
Each render thread just takes the newest finished state without waiting, sends
newly finished assets to the graphics card, and draws.

| Sub-issue | What it builds |
|---|---|
| 110a | The ceramic engine (this project's improved copy) in the W client's build, with its tests |
| 110b | The window's render thread: reads window events and hands them in, then draws |
| 110c | The three-buffer mailbox, extrapolation, and corrections that snap into place (from this project's 515c and 515d) |
| 110d | The append-only asset table, with loading done as stations; this retires the read-ahead thread |
| 110e | Posing, particles and in-view checks as stations, in chunks; measured at 500 and 5,000 figures |
| 110f | More render threads: one with no window (map browser previews, W04 comparisons), and a second view of the world |

The design has to fit four hard limits:

- **One thread per context.** An OpenGL context accepts commands from one thread
  at a time, so drawing can never be a station.
- **Window events stay on the first thread.** GLFW (which raylib sits on) only
  reads window events on the process's first thread. So "no main thread" means
  that thread becomes the window's render thread and does no game work.
- **raylib's drawing layer is global.** It keeps one set of drawing state for
  the whole process, so two render threads can't both draw through it. Either
  the extra threads draw through a small layer of the client's own, or raylib
  gets a reversible patch.
- **The graphics card runs one context's work at a time.** Several contexts let
  several threads prepare drawing commands at once, but they don't make the card
  itself faster. Picture-in-picture can also be done by drawing the second view
  into a texture within one context. 110f builds it both ways and measures them.
  The windowless thread gets built either way, because it has to run while the
  window draws.

## The clock

Your sketch, read as a mechanism: there is no clock thread. Each time a worker
picks up a task, it first compares the time against the registry's earliest
deadline. That's one read and one comparison. If the deadline has passed, the
worker hands in the tasks that are due. Checking the clock rides on work that's
already happening.

The gap is when nothing is happening. If every worker is idle, none of them
takes a task, so none reads the clock, and a due entry waits for some unrelated
task to arrive. Something has to notice the moment. Two candidates:
- **(a) The render thread checks too.** It's awake every frame anyway, so it can
  do the same comparison. The worst lateness is one frame, about 16 ms.
- **(b) The last idle worker sleeps until the earliest deadline.** This is a
  sleep with a fixed end, so it isn't spinning. It is a sleeping thread, though,
  which you wanted to avoid.

Which would you accept: being up to one frame late, or a thread that sleeps but
wakes at a set time? The issue also asks how to store the registry: a timing
wheel (a ring of buckets, one per time step, where adding and firing cost the
same however many entries there are) or a sorted list.

## The browser page

What separates a small HTML renderer from a full engine is whether the page has
to change without being redrawn from scratch. Static layout, text, images and
links are cheap. Typing into a search box and watching the list narrow, or a
download button that shows its progress, needs either scripts or the client
redrawing the page after every event.

Which of those does the browser need to do? Going the other way: if you picture
someone picking a map, what is the one thing they'd try to do that a still
picture of a page couldn't do?
