## What `--mirror` does


When you pass `--mirror`, two things happen before the upload (lines 179–184):


```bash

if $MIRROR; then

echo "Clearing remote ${REMOTE_DIR}/ for a clean mirror ..."

if "$NEOCITIES" list "$REMOTE_DIR" >/dev/null 2>&1; then

"$NEOCITIES" delete "$REMOTE_DIR" || die "remote delete of ${REMOTE_DIR}/
failed"

fi

fi

```


1. It checks whether the remote `similar-different/` directory exists
(`neocities list "$REMOTE_DIR"`).

2. If it does, it deletes **that path specifically** (`neocities delete
"$REMOTE_DIR"`), then re-uploads everything fresh.


The critical variable is on line 78:


```bash

REMOTE_DIR="similar-different" # the ONLY live-site section this script writes

```


The delete command targets `"$REMOTE_DIR"` — i.e. literally `neocities delete
similar-different`. The Neocities API treats that as "delete the
`similar-different` directory and its contents." It is a **named, relative
path**, not a root-level wipe. There is no `/` prefix making it
absolute-to-root, and there is no recursive root target anywhere in the script.
So the rest of your site (homepage, other sections) is never named and never
touched.


`★ Insight
─────────────────────────────────────`

- **Why the whole site is safe by construction:** the script's entire design rests on Neocities' `push` command only being able to upload to the *site root*. To land files under a subdirectory, it stages a directory that *contains* `similar-different/` and pushes that wrapper (see the header comment, lines 12–17). Because every remote operation is expressed relative to that one subdirectory name, the blast radius is structurally limited to `similar-different/`.

- **`--mirror` only changes deletions, not scope:** without it, the push is incremental (changed/new files upload, stale remote files linger). With it, you get a clean slate — but "clean" still means "clean *within `similar-different/`*," never the whole site.

- **The `list` guard prevents a spurious failure:** it only attempts the delete if the directory exists, so a first-ever mirror deploy won't `die` on trying to delete something that isn't there yet.

`─────────────────────────────────────────────────`


## The one thing to verify yourself


The safety hinges entirely on Neocities' `delete` treating `similar-different`
as a directory path and **not** descending or affecting siblings. That's
standard Neocities behavior, but since this is your live public site, the
bulletproof way to confirm is a dry run — which deletes nothing:


```bash

scripts/deploy-to-neocities --dry-run

```


That stages into RAM and runs `neocities push --dry-run`, showing the exact
upload list while touching nothing live (lines 147–156). It won't exercise the
`--mirror` delete path, but it confirms the staging only ever contains
`similar-different/`.


If you want absolute certainty about the delete before ever running `--mirror`,
the highest-value check is to list your live site's top-level entries first:


```bash

neocities list /

```


That shows you everything at root, so you can confirm `similar-different` is one
entry among your other untouched sections — and that deleting it leaves the
rest intact.


**Bottom line:** `--mirror` will not delete your entire website. It deletes and rebuilds only the `similar-different/` directory. Everything is anchored to the single `REMOTE_DIR="similar-different"` variable, and nothing in the script ever references the site root as a delete target.
