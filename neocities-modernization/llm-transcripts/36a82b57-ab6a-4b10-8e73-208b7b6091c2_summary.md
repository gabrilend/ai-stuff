## Why it's slow (yes, you nailed it)


You asked "are we moving things on and off the GPU too often?" The literal
answer is **no, we don't move data per iteration** — embeddings get uploaded

But we're moving **control** to the GPU and back every iteration, and that's the
killer:


`★ Insight
─────────────────────────────────────`

Look at `vkc_dispatch` at `vk_compute.c:919`: every single call ends with
`vkWaitForFences(..., UINT64_MAX)`. That's the CPU thread sleeping inside the
kernel until the GPU signals "this one dispatch is done." Then the CPU wakes,
runs a handful of Lua statements (`check_result`, the `% 100` check, loop
increment), records a *brand new* command buffer with `vkBeginCommandBuffer(...

dispatch is a tiny amount of GPU work (3584 workgroups × ~microseconds each)
wrapped in tens to hundreds of microseconds of CPU + driver overhead. The GPU
sits idle between dispatches. This is the textbook "kernel launch overhead
dominates compute" anti-pattern — the GPU has ~3000 cores ready, but they only
run for a fraction of each iteration's wall-clock, because the CPU keeps
stopping them to ask "you done yet?"

`─────────────────────────────────────────────────`


A few sane fixes, from quick to deep:


1. **Record many iterations into one command buffer, submit once.** Today's loop
submits 8358 command buffers per batch. Recording N iterations into a single
buffer (with `vkCmdPipelineBarrier`s between dispatches to express the
read-after-write dependency on `output_buf`) and submitting once means one fence
wait instead of N. Easy win, but it does require the shader-side iteration
dependency to be expressible as Vulkan memory barriers (which it should — each
iteration reads `output_buf` written by the previous one).

2. **Use multiple frames-in-flight.** Keep two or three command buffers and
fences cycling: while the GPU works on iteration N, the CPU records iteration
N+1 into a different buffer. Hides the CPU/driver cost behind GPU work. Bigger
refactor.

sequence in shared memory and runs all 8358 iterations internally. One dispatch
per batch instead of 8358. This is the architecturally correct version — the
iteration is per-workgroup-sequential anyway, so the GPU was always the right

biggest single win.

## What "1 iteration" actually means


An "iteration" here is **one round of greedy picking across the entire batch of
sequences in parallel**. In a single iteration:


- All 3584 workgroups run simultaneously, one per sequence-in-progress.

- Each workgroup scans all 8359 poems looking for the one most "diverse" from its sequence's current centroid.

- The winning poem gets appended to that sequence.

- The mask and centroid get updated.

- One slot got filled for **every** sequence in the batch.


So "1 iter in 0.8 s" is not "we picked one poem in 0.8 seconds" — it's "we
picked **3584 poems** in 0.8 seconds, one for each sequence in the batch."
Across the whole run, you need 8358 iterations × 3 batches = 25,074 iterations
to fill in 8359 sequences × 8358 slots = ~70 million slots total. Each
iteration moves a wave of 3584 slots forward at once.


`★ Insight
─────────────────────────────────────`

The reason one "iteration" is conceptually small but computationally huge is the
**shape** of greedy farthest-point selection. You can parallelize across the
*outer* loop (different starting seeds → different sequences → different
workgroups) all you want, and we are: 3584-way at a time. But within a single
sequence, you **can't** parallelize the iterations against each other — pick N
depends on what pick 1..N-1 selected. So you serialize on the dimension where
each step is small-but-data-hungry. Each step has to re-scan the full 25 MB
embedding table because "which poem is furthest from the current centroid"
requires looking at every candidate. That's why memory bandwidth dominates:
we're effectively streaming the entire embedding table through the GPU's memory

In rough terms, here's the access pattern the current code produces:


- Workgroup K's threads stride through the embedding table reading poems 0, 256, 512, ..., 8192.

`★ Insight
─────────────────────────────────────`

There are **two completely different synchronization mechanisms** in Vulkan

thing. They're not — they operate at different scopes and on different sides
of the CPU/GPU boundary.


- **`barrier()`** (a GLSL builtin) is workgroup-internal. It synchronizes the 256 threads within a single workgroup. It cannot reach across workgroups, even within the same dispatch.

- **`VkFence` + `vkWaitForFences()`** is host-side. The CPU uses it to wait until the GPU has finished an entire submission. It doesn't synchronize anything *inside* the GPU's execution of a single dispatch — it just signals "the GPU finished everything in this submission" to the CPU.


These never contradict each other; they're operating on different objects. I
gave a clean explanation of `barrier()` earlier and then sloppily said "fence
wait enforces cross-workgroup ordering" without explaining the *mechanism*.

## How fences actually give the cross-workgroup ordering


The "dispatch per tile" option doesn't work because fences magically synchronize
workgroups inside a running dispatch. It works because **fences let you sequence
submissions**, and submission boundaries are the *only* place where you can
enforce "all workgroups for X finished before any workgroup for Y started."
Here's the sequence:


1. Build a command buffer containing dispatch-for-tile-0.

2. Submit it to the queue. The GPU starts spinning up workgroups.

3. CPU calls `vkWaitForFences()`. CPU blocks here.

4. GPU runs all workgroups for tile 0 to completion. The submission's final work
item finishes. The fence is signaled.

5. CPU wakes up.

6. CPU builds a new command buffer containing dispatch-for-tile-1, submits it,
etc.


The fence in step 3-5 doesn't reach into the GPU and force-sync workgroups. It
just tells the CPU "the GPU is done with the previous submission, you can move
on." The reason this gives the lockstep guarantee is that **the submission is
the unit of work that completes atomically as a whole**. By the definition of
"submission complete," every workgroup in that submission has run. Then — and
only then — the CPU adds the next dispatch to the queue.


If you tried to put tile 0 and tile 1 dispatches in the *same* command buffer
back-to-back without a barrier in between, you'd get **no ordering guarantee**
between them: the GPU is free to execute commands in a buffer out of order
unless you explicitly insert a `vkCmdPipelineBarrier` to introduce a memory
dependency. The pipeline barrier inside a command buffer is the in-flight
equivalent of the fence wait — it's the thing that says "wait for everything
pipelined up to this point before starting what comes after."


## So my earlier statements were both right — separately


The two things I said that look like they conflict are:


- "`barrier()` is workgroup-internal" — true. `barrier()` is a *thread* sync primitive.

- "The fence wait between dispatches forces all workgroups to finish tile 0 before any start tile 1" — true. The fence wait doesn't sync workgroups directly; it makes the CPU wait for the *submission* to complete, and the next dispatch can't start until the CPU submits it after waking up.

separate submissions** (or in the same command buffer with a pipeline barrier

`★ Insight
─────────────────────────────────────`

This is a useful general lesson about GPU sync that's worth burning into memory:
**scope of synchronization is determined by where the sync primitive lives**,
not by what it's called. A barrier inside a shader syncs threads in a workgroup.

- Tightest: `barrier()` — threads in one workgroup

- Tighter: `vkCmdPipelineBarrier` — commands in one command buffer

- Loose: `VkSemaphore` — queue-to-queue on the same device

- Loosest: `VkFence` — CPU-GPU handshake across an entire submission

different scopes, gives different guarantees.

## Question 1: Can the CPU work during step 4?


**Yes — that's a real optimization, and it's called "pipelining" or "multiple frames in flight."** I actually mentioned it as option 2 way back when we were first discussing per-dispatch overhead, but I didn't make the connection now. The pattern is:


- Allocate **two** command buffers and **two** fences instead of one.

- Submit command buffer A. While the GPU runs A, the CPU starts recording command buffer B with the *next* dispatch.

- When fence A signals (GPU done with A), the CPU has already finished building B. Submit B immediately and start building C in A's recycled slot.

- The CPU and GPU run in parallel; per-dispatch CPU overhead disappears into the gaps.

## What an "iteration" actually is


In this algorithm, an iteration is one **round of greedy picking across every

- Each workgroup picks one more poem for its sequence.

- That iteration is done.


The thing that determines how many iterations are needed is **how many picks

sequence is a ranking of all 8358 other poems, so each sequence needs 8358
picks. That's true whether you're building 3584 sequences in parallel or 1191.

| | Batch 1 | Batch 2 | Batch 3 |

|---|---|---|---|

| Workgroups | 3584 | 3584 | **1191** |

| Iterations | 8358 | 8358 | 8358 |

| Picks per iter | 3584 | 3584 | **1191** |

`★ Insight
─────────────────────────────────────`

The reason this is structured as "iterations × workgroups" rather than "total

algorithm both rely on this "every workgroup in the batch is at the same step"
invariant, because each pick depends on the centroid which depends on what's
already in the sequence. So the iteration count is determined by the sequence
*depth*, not the batch *breadth*. Breadth (workgroup count) affects total work
per iteration; depth (iteration count) is fixed by what a sequence is.

## Reason 1: Your 1080 Ti's FP16 is artificially crippled


This is the big one for *your* situation specifically. NVIDIA introduced FP16
with the Pascal architecture but deliberately gave it different throughput
depending on the chip:


| Pascal chip | Product | FP16 throughput vs. FP32 |

|---|---|---|

| GP100 | Tesla P100 (data center) | **2× FP32** (packed math, full speed) |

| GP102 | **GTX 1080 Ti**, Titan Xp | **1/64 FP32** (crippled) |

| GP104 | GTX 1080, 1070 | 1/64 FP32 (crippled) |

| GP106 | GTX 1060 | 1/64 FP32 (crippled) |


This wasn't a hardware accident — it was deliberate market segmentation.
NVIDIA wanted to keep full-speed FP16 as a data-center-only feature so people
who needed FP16 throughput (ML training) had to buy P100s instead of $700
consumer GPUs. The FP16 *capability* exists on consumer Pascal (your shader will
compile and run), but each FP16 multiply takes **64×** longer than the FP32
equivalent.


So on a 1080 Ti specifically, if we wrote the dot-product loop to multiply in
FP16, every iteration of that 768-element inner loop would run 64× slower. The
bandwidth win from FP16 storage (~2×) would be swamped by the compute
regression (~64×) and the whole thing would end up dramatically *slower* than
today's FP32 code.


The compute-as-FP32 pattern routes around the cripple: we keep the *fast* path
(FP32 ALU ops) and only use FP16 for the *narrow* path that's actually faster
(memory bandwidth between VRAM and the compute units).


`★ Insight
─────────────────────────────────────`

This is the kind of hardware detail that lives in NVIDIA's whitepapers but

## Reason 2: FP32 accumulators are best practice everywhere


Even on hardware where FP16 compute is fast, the **accumulator** of a long sum
should be FP32. This isn't a Pascal thing — it's a numerical-precision thing
that bites every GPU.


A cosine distance involves summing 768 multiplications:


```

dot_product = sum_{i=0..767} centroid[i] * embedding[i]

```


If each multiply produces an FP16 result and you accumulate in FP16, you have an
11-bit mantissa (10 stored, 1 implicit). After summing ~50-100 terms, the
accumulator gets large enough that small new additions lose precision — adding
`1e-3` to `1.5e1` in FP16 loses the addition entirely because the FP16
representable steps near 15 are larger than 1e-3.


This is **catastrophic cancellation** for dot products. The standard fix used by
every fast GPU math library (cuBLAS, cuDNN, FlashAttention, etc.) is:


- Multiply FP16 × FP16 → result in **FP32**

- Accumulate the FP32 results into an FP32 accumulator

- Optionally convert the final answer back to FP16


Tensor cores on V100+ literally have this built in: they take FP16 inputs and
produce FP32 outputs in hardware. The reason isn't hardware preference — it's
that the FP16 accumulator path produces numerically wrong answers for vectors of
any meaningful length.


For your specific case with 768-element dot products from 2560-D embeddings
(qwen3-embedding:4b), the FP16 accumulator would lose ~3-4 digits of precision
over the sum. The ranking of cosine distances could shift — meaning your
diversity sequences could come out *different from the FP32 reference*, which
violates the "output bit-identical-equivalent" guarantee we wrote into 9-014.


## The combined effect


The `load FP16, compute FP32` pattern gets you the best of both worlds, both on
Pascal *and* on every other architecture:


1. **Bandwidth win:** the FP16 storage means each read transfers half as many
bytes through the memory hierarchy. The 25 MB embedding table becomes 12.5 MB;
the L2 cache holds twice as much; per-iteration memory traffic halves. This is
the 1.8-2× speedup we wrote into the issue.

2. **Compute correctness:** the FP32 accumulator preserves precision so the
output ranking is identical to today's all-FP32 path.

3. **Portability:** on newer GPUs, the same code automatically benefits from
native FP16 loads (they're already free on Volta+) without any compute
regression on older hardware.


`★ Insight
─────────────────────────────────────`

There's a useful general rule lurking here: **"the optimal precision for storage
and the optimal precision for compute are not always the same."** Storage cares
about how many bytes you move; compute cares about how much error accumulates.
For workloads where you move a lot of data through arithmetic that sums many
terms — dot products, convolutions, attention — the right answer is almost
always "narrower for storage, wider for accumulators." Diffusion models do this
with FP16/BF16 weights and FP32 accumulators; LLM inference does it; cuBLAS does
it. Diversity sequence ranking is just another instance of the same shape.

### Assistant Response 34

You caught a real conceptual snag — and untangling it actually illustrates how
the GPU memory hierarchy works, which is worth knowing. The short answer:
**cache and compute are different stages.** Cache holds bytes; compute happens
in registers; the cast from FP16→FP32 happens *between* them, not in either of
them.


## The memory hierarchy in stages


When a shader thread executes a single line like `float e_val =
float(embeddings[base + d])`, here's the actual data flow:


```

[ VRAM (GDDR) ] "the embedding[base+d] bytes live here as 2 bytes"

│

│ fetch 2 bytes (FP16-sized)

▼

[ L2 cache ] "holds 2 bytes per value, shared across SMs"

│

│ fetch 2 bytes (FP16-sized)

▼

[ L1 cache ] "holds 2 bytes per value, per-SM"

│

│ fetch 2 bytes into a register

▼

[ FP16 register ] "holds the raw FP16 bits, briefly"

│

│ cast instruction (one GPU op, register-to-register)

▼

[ FP32 register ] "holds the unpacked FP32 value, fed to the multiplier"

│

│ fed into the FP32 ALU

▼

[ FP32 multiplier ] "this is where the * happens"

```


The cache **never sees the FP32 form** of these values. The cache just holds the
raw 2-byte representations. The FP32 form only briefly exists in a register,
where it gets fed straight into the multiply unit and then the result of the
multiply gets accumulated in another FP32 register.


`★ Insight
─────────────────────────────────────`

The mental model that produces the confusion is "cache holds *computed values*"
— like the cache is mid-computation. But the cache is genuinely just a storage
layer for raw bytes. It has no idea what those bytes mean. They could be FP16,
FP32, int8, packed pixels, or a JPEG header — the cache hardware treats them
as opaque memory. The interpretation happens at the moment the bytes reach a
register and the compiler-emitted instruction says "treat this as float16_t" or
"cast this to float". The instruction is what gives the bytes a type; the cache
is type-agnostic plumbing.

`─────────────────────────────────────────────────`


## So where's the actual win?


The bandwidth savings happen at every level of the hierarchy where the *byte
size* matters:


- **VRAM→L2 bandwidth:** today's FP32 layout transfers 4 bytes per value through the memory bus; FP16 transfers 2. Halves the bytes-per-second pressure on the most contested resource.

- **L2 capacity:** the L2 holds a fixed number of bytes (~5.5 MB on a 1080 Ti). FP16 means twice as many *values* fit. That's the "effectively doubles the cache's usable capacity for embedding data" thing.

- **L2→L1 bandwidth:** same halving.

- **L1→register bandwidth:** same halving.

- **Cache line utilization:** the GPU fetches memory in fixed-size lines (128 bytes on Pascal). An FP32 line holds 32 floats; an FP16 line holds 64 values. So a single line fetch delivers 2× more useful data per fetch.


Every byte that moves between any two layers of the hierarchy moves at half the
cost. Only the multiplication itself, which happens *after* all that movement,
runs at FP32.


## Concretely, what each unit "sees"


Here's the same dataflow expressed as what each piece of hardware perceives:


| Stage | What it sees | Width |

|---|---|---|

| VRAM | "byte stream" | 2 bytes per embedding value |

| L2 cache | "byte stream" | 2 bytes per embedding value |

| L1 cache | "byte stream" | 2 bytes per embedding value |

| Load instruction | "fetch 2 bytes, place in register as FP16" | 2 bytes in /
16 bits out |

| `float(...)` cast | "expand 16 bits to 32 bits" | 16 bits in / 32 bits out |

| `*` operator | "FP32 × FP32 → FP32" | 32 bits in / 32 bits out |

| `+=` accumulator | "stays FP32 throughout" | 32 bits |


Notice that "FP16" is the answer for the first three rows (the memory hierarchy)
and "FP32" is the answer for everything from the cast onwards (registers + ALU).
The boundary between them is exactly **one register-to-register cast
instruction**, which is essentially free on every GPU.


## Quick analogy


Think of the cache as a parking garage and the compute units as the cars
themselves. The garage holds vehicles; the cars hold passengers. We're saying
"make the cars smaller in the garage" — they take up half the parking spots,
so we can park twice as many. When a car actually needs to drive somewhere, the
engine still runs at full power; the smaller-car decision didn't change how fast
the engine spins.


The "cars stay small while parked, full-size while driving" sounds paradoxical
but it's just two different states of the same vehicle: compact-stored vs.
fully-deployed. FP16 is the compact-stored form; FP32 is the fully-deployed
form.


## Bringing it back to your question


You asked "if we're computing with the values in cache, how could the values in
cache be FP16?" The answer is **we're not computing with the values in cache**
— nothing computes in cache, ever. We're computing in registers, with values
that briefly *visit* registers from the cache. The cache holds them in FP16
(saving bandwidth and capacity), the register holds them in FP32 (so the math is
precise and fast on your hardware), and the conversion is one cheap instruction
that happens at the moment they cross between the two.


That's why "FP16 storage, FP32 compute" is a real thing and not a contradiction
— it's literally describing the byte width at each layer of the hierarchy, and
those layers genuinely can have different widths because they're physically
different chips inside the GPU.
