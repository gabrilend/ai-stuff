## Two apps hitting the same llama-server


llama-server has a `--parallel N` (a.k.a. `-np N`) flag that controls how many
concurrent slots it holds. Each slot is its own KV cache and runs its own
sequence; requests beyond N queue in-process (the HTTP connection stays open,
waiting).


```bash

llama-server -m model.gguf --embedding --parallel 4 ...

```


With `--parallel 4`, four embedding requests can be in flight simultaneously,
sharing a single GPU forward pass via *continuous batching*. This is the key
efficiency trick: instead of "run forward pass for request A, then for request
B," the GPU runs forward(A,B,C,D) in one pass on a wider batched matrix
multiply. Throughput goes up roughly linearly with parallelism until you hit
VRAM limits.


Default `--parallel 1` (which our `start-llamacpp-server.sh` uses) serializes
requests. If app A sends an embedding request and app B's request arrives before
A finishes, B waits. Same FIFO queue, just no batching speedup.


For our embedding workload specifically: nomic-embed-text v1.5 is small (~270 MB
at FP16), so each parallel slot's KV cache is tiny. You could probably get away
with `--parallel 8` or `--parallel 16` on a 1080 Ti's 11 GB without straining
VRAM. We don't currently set this — adding it would be a one-line tweak to
`start-llamacpp-server.sh`.


## Queueing behavior


- **In-flight, beyond N slots**: HTTP request waits in the server's request queue, connection held open, no client-side error

- **No persistence**: if the server crashes mid-queue, those requests are lost (the client sees a connection reset)

- **No prioritization**: FIFO across all clients — app A and app B share one queue

- **No per-client rate limiting**: any client can monopolize all N slots


## Two different models on llama.cpp


**One llama-server process serves exactly one model**, loaded at startup, never swapped. To serve two models, you spin up two `llama-server` processes:


```bash

# Process 1: embedding model on port 18080

llama-server -m nomic-embed-text-v1.5.gguf --embedding --port 18080


# Process 2: chat model on port 18081

llama-server -m qwen3-7b.gguf --port 18081

```


Each owns its own GPU memory. Two processes on one GPU = each gets a share of
VRAM; you must size them so they fit together. For our project this is wide open
— our `inference_servers` config could grow new entries:


```lua

"nomic-embed-text-v1.5", model_path = "..." },

{ name = "local-qwen", host = "127.0.0.1", port = 18081, model =
"qwen3-embedding", model_path = "..." },

```


Then callers select the server with `--server=local-nomic` or
`--server=local-qwen` per pipeline run.


## How Ollama differs


Ollama is a *higher-level orchestration layer* around llama.cpp. The big shape
differences:


| Concern | llama-server | Ollama daemon |

|---|---|---|

| Models held in memory | Exactly 1, baked in at process start | N, loaded on
demand by name |

| Model switching cost | Restart the process (seconds) | Dynamic load/unload
(seconds; ~time to seek and mmap) |

| Concurrency | `--parallel N` per process | Per-model parallel pool; queued if
model needs swapping |

| Model registry | None — you supply paths | Built-in `ollama pull` from their
hub |

| Multi-model in one HTTP server | No | Yes (request's `model` field selects) |

| HTTP shape | OpenAI-compatible from the start | Ollama-native +
OpenAI-compatible layer added later |


Ollama's "one daemon, many models" model is convenient for casual single-user
usage: `ollama run llama3` and `ollama run codellama` work from the same daemon.
But the dynamic load/unload means cold-start latency hits whenever you switch
— for a pipeline processing 8000 poems, you'd never switch mid-batch anyway,
so this convenience is wasted.


llama.cpp's "one process, one model" model is leaner: no model-registry HTTP
plumbing, no swap thrash, the server's only job is serving inference. For our
pipeline (one model used heavily), it maps cleanly: one server runs through the
whole batch with the model resident the whole time.


## What's "queued" vs "rejected"


Neither engine returns 429 (Too Many Requests) by default. Both queue.
Differences:


- **Ollama**: requests for model X queue together. Requests for model Y (not currently loaded) trigger an unload-and-reload of X before Y can serve.

- **llama-server**: all requests share one queue (since there's only one model). No load/unload paths to thrash through.


For "what happens if 100 clients hit simultaneously":

- llama-server with `--parallel 4`: 4 process in parallel, 96 wait in queue, all complete in order

- Ollama with `--parallel 4`: same, *as long as they all want the same model*; otherwise model swaps interleave with request servicing and throughput tanks


## Implications for our project


We don't multi-model. The whole embedding pipeline uses one model file resident
on disk. That makes llama.cpp's "one process per model" the cleaner fit — we
save the ~50 MB of memory overhead Ollama uses for its registry/control-plane,
get OpenAI-compatible endpoints natively (no translation layer), and avoid any
dynamic model-load behavior we don't need.


If you ever do want multiple models, the natural pattern is:

1. Add entries to `inference_servers` for each model

2. Run one `start-llamacpp-server.sh --server=<name>` per entry (each binds to
its configured port)

3. Each pipeline stage that wants a specific model passes `--server=<name>` and
gets routed to the right port via `inference_config.build_host_url()`


The current schema supports this; we just don't exercise it. The cost is
operational (you launch and manage N processes instead of 1), but you also get N
times the concurrency limit, since each process has its own `--parallel` pool.
