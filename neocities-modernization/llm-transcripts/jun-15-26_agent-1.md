# Refactoring Report — Neocities Poetry Modernization


The codebase is **~28k lines of Lua plus ~5.5k lines of shell**, organized
around a seven-stage pipeline (extract → validate → embed → similarity →
diversity → HTML → publish). It has grown by accretion through 14+ phases,
and the seams now show. Below are the refactoring opportunities ranked by impact
and confidence.


`★ Insight
─────────────────────────────────────`

This codebase shows a classic pattern of *parallel evolution* — the same
concept (HTML escaping, config loading, similarity lookup) gets re-implemented
inside each module rather than imported. It usually starts as deliberate
isolation early in a project, then becomes accidental duplication after a few
phases. The fix isn't to centralize aggressively, but to pick one canonical
implementation per concept and route the rest through it.

`─────────────────────────────────────────────────`


---


## 1. Decompose the 4,612-line HTML generator (highest impact)


The file at `src/flat-html-generator.lua` is the single biggest target. It
contains **77 functions** across four largely independent concerns: pagination
math, poem-formatting (golden/boost/regular variants + content warnings +
markdown), ranking & cache loading, and per-page-type output orchestration.


**Proposed split into four siblings:**

- a pagination helper (page sizing, slicing, prev/next nav links)

- a poem-formatter (escape, markdown, golden/boost frames, content warnings)

- a ranking front-end (loads precomputed similarity/diversity caches, serves recommendations)

- a page-type dispatcher (chronological index, paginated lists, similarity pages, diversity pages, similarity/diversity text archives)


The current file is hard to navigate even with vim folds. Splitting along those
four seams would yield modules in the 800–1,400 line range and make the
poem-formatting logic reusable for the centroid and word-page generators that
currently re-create parts of it.


**Risk:** medium. The four sections share a few helpers (the local `escape_html`, color gradient computation) — those need to be extracted first into a shared primitives module before splitting.

## 2. Eliminate three independent HTML-escape implementations (highest confidence)


I verified this directly: an HTML-escape function is defined three separate
times.


- `src/flat-html-generator.lua:1486` — a local function with only 3 substitutions (missing apostrophe/quote escapes, per a comment referencing an open issue)

- `src/html-generator/template-engine.lua:19` — module-level, 5 substitutions

- `src/html-generator/golden-poem-indicators.lua:13` — module-level, identical 5 substitutions to the template-engine


The flat-html-generator version is actually weaker than the other two (fewer
entities escaped). This is exactly the kind of bug-farm the user's convention
about avoiding silent fallbacks aims to prevent — different code paths get
different escaping, which means the same poem text renders differently depending
on which page it's on.


**Action:** extract one canonical implementation into `libs/html-escape.lua` (or add to `libs/utils.lua`), then make all three sites import it. ~30 lines of code change, removes a class of bugs.

## 6. Consolidate the three config-loading entry points


Three modules each call `pcall(dofile, "/config.lua")` independently with their
own project-root-detection logic:


- the unified config-loader (the one that's *meant* to be canonical)

- the Ollama config wrapper

- the data-sources loader


This is the duplication-by-isolation pattern from the insight above. The fix is
small: make the Ollama and sources modules depend on the unified loader rather
than re-implementing the load. Project-root detection (currently includes a
hardcoded fallback path) belongs in a single utility function.


**Why it matters:** every place that detects project root independently can drift. The hardcoded `/mnt/mtwo/...` fallback path will silently bite anyone who clones the repo to a different location.


---


## 7. Split the 1,573-line `run.sh` driver


This bash script does CLI parsing, ten stage executors, an interactive TUI, and
logging in one file. Natural seams:


- a `lib/cli-parser.sh` for the ~100-line argument case statement

- a `lib/pipeline-stages.sh` for the ten stage functions

- a `lib/interactive-mode.sh` for the TUI menu (~250 lines)

- a `lib/logging.sh` for color and log helpers that `generate-embeddings.sh` could also share


`★ Insight
─────────────────────────────────────`

Bash scripts past ~500 lines hit a readability cliff because bash has no real
module system — every function shares one namespace. Splitting with `source
lib/foo.sh` is the bash equivalent of imports, and helps a lot. The trick is
keeping each lib file *only* declarations: no side-effects at source time, so
order doesn't matter.

`─────────────────────────────────────────────────`


The shared logging helpers in particular would clean up `generate-embeddings.sh`
(950 lines) at the same time.

## 8. Smaller follow-ups (worth doing but lower urgency)

- **Two validation runners** — `run-validation.lua` and `run-validation-with-reports.lua` overlap heavily and neither is called by `run.sh`. Either wire the reports-flavored one into the main pipeline, or collapse them to one runner with a `--reports` flag.

- **Logger bypassed by direct prints** — the shared `utils.log_info / log_warn / log_error` family exists but is bypassed in dozens of files. New code should funnel through it. Leave existing `io.write` for progress bars (legitimate use).

## What NOT to refactor (one anti-recommendation)


The three similarity-engine files might look duplicated by name, but they
aren't. One is a batch embedding generator, one is its multithreaded version,
and the small one in `html-generator/` is a render-time lookup helper. **Leave
them as three modules** — merging them would conflate layers (compute vs.
parallel-dispatch vs. read) that benefit from being separate. The user's
instinct to keep batch and rendering paths apart is correct here.
