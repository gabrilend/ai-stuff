# 002 — The Map and Its Milestones

**Datapath document.** Covers the static world: what the ground is made of, how a
soldier knows which way to walk, and how the game answers "which lane is in the
most trouble?" without ever measuring a straight-line distance.

## The ground is a graph, not a grid

There is no terrain, no jungle, and no off-road movement. Everything that walks,
walks on a **path graph**: a fixed set of numbered points joined by edges. A
soldier's position is always "on the edge between point 14 and point 15, 0.62 of
the way along." This is chosen over a tile grid or free 2D steering for three
reasons:

1. Pathfinding collapses to "read the next node id out of an array." No A*, no
   flow field, no per-tick search. With a thousand soldiers on the map that
   difference is the whole frame budget.
2. "How far has this lane been pushed" becomes a small integer comparison rather
   than a geometry problem. See *milestones*, below.
3. The graph is authored once and never changes at runtime, so it can live in a
   flat, cache-friendly array and be shared read-only across every worker thread
   in the simulation's pool.

The graph is generated by a map-building tool, not typed out by hand. There is no
map editor and no map file format to hand-edit; the tool takes the handful of
shape parameters below and emits the node array.

## The shape

Two bases at opposite corners of a square field. Three lanes join them:

- **Lane 1 (top)** leaves team 1's base heading up, turns right at the top-left
  corner, runs along the top edge, turns down at the top-right corner, and enters
  team 2's base.
- **Lane 2 (center)** runs corner to corner in a straight diagonal. It has no
  turns and therefore no junctions of its own.
- **Lane 3 (bottom)** mirrors lane 1 along the bottom and right edges.

The two corners on each side lane are **junctions**. Four junctions exist in
total. Each junction is joined to the center lane by a short **connector** edge —
this is the ground that used to be jungle, with everything that made it jungle
taken out of it. Nothing spawns on a connector, nothing camps there, and no
tower covers it. It exists so that a hero can change its mind about which lane
it is fighting in. Side lanes do not connect to each other; the only way from
top to bottom is through the center.

## Lanes have a width, and the center's is greater

Each lane carries a **width** in paces: how many bodies can stand abreast in it
before the ones behind have to queue.

**The center lane is wider than the side lanes.** Permanently, as topography —
not as a rule that switches on during a challenge.

The immediate reason is the third challenge. All three lanes' worth of soldiers
funnel into the center during a challenge, and a challenge monster has to be able
to fight a whole team at once; in a single-file corridor that is not a battle,
it is a queue waiting its turn to die. See
[boons and the challenge](015-boons-and-the-challenge.md).

The consequence is permanent and larger than that, and it is worth stating as a
design property rather than a side effect: **the center lane is where numbers
matter most.** Two even teams meeting in a side lane fight rank against rank, and
a fourth soldier behind the front three contributes nothing until somebody dies.
The same two teams meeting in the middle get more of their bodies into contact at
once, so a numerical advantage converts into a killing advantage faster.

That makes the three lanes meaningfully different from each other for the first
time, and it does so without a single special rule — one number in the map
builder's parameter table, read by the frontline queue. A team that has stacked
its upgrades into the top lane is playing a game about *quality*, because the top
lane will only ever let three of them fight. A team that has stacked the center
is playing a game about *quantity*.

The width feeds two things and nothing else: how many bodies the frontline queue
lets stand abreast (see
[a unit and what it carries](004-a-unit-and-what-it-carries.md)), and how wide
the renderer draws the lane. It is not a movement constraint — soldiers still
walk the path graph, and width only decides how many of them may stop at the same
point on it.

## Milestones: the only measure of progress

Each lane carries an ordered list of nine **milestones**, numbered 0 through 8,
running from team 1's library to team 2's library:

| Index | What stands there |
| --- | --- |
| 0 | Team 1's library |
| 1 | Team 1's base guard tower for this lane |
| 2 | Team 1's inner lane tower |
| 3 | Team 1's outer lane tower |
| 4 | The midpoint — where waves meet on an even game |
| 5 | Team 2's outer lane tower |
| 6 | Team 2's inner lane tower |
| 7 | Team 2's base guard tower for this lane |
| 8 | Team 2's library |

A team's **push depth** in a lane is the highest milestone index reached by any of
its **living** soldiers there, from that team's point of view. Team 1 pushing to
index 6 and team 2 pushing to index 2 describe the same lane from opposite ends,
and the code stores one number per team per lane rather than trying to keep a
single signed value.

**Living**, not a high-water mark — so push depth can go down. It creeps up as
soldiers advance, and it collapses when they die. It collapses completely twice a
match, during **the calm** after a challenge, when every soldier on the field
turns around and walks home. That is the one moment where maintaining the number
incrementally is not enough and a full recompute is needed, and it is worth a
comment at the call site saying so. See
[boons and the challenge](015-boons-and-the-challenge.md).

Every question the game asks about lane state is a comparison of these small
integers. In particular: when a hero is spawned on the library and has to pick a
lane, it picks the lane where the **enemy's** push depth is greatest. The vision
is explicit that this is not a distance question — a lane where the enemy sits
one pace past the first tower is in less trouble than a lane where the enemy is
inside the base, even if the base is physically closer to the library. Milestone
comparison gets that right for free; a distance check gets it exactly backwards.

## The records

Everything below is a plain array-of-structs laid out once at map build time.
Fields are given down to the primitive.

### node

| Field | Type | Meaning |
| --- | --- | --- |
| `id` | integer | Its own index in the node array. 1-based. |
| `x`, `y` | double | Position on the field, in paces. Used for drawing and for weapon range only. |
| `kind` | integer | 1 = plain lane point, 2 = junction, 3 = tower site, 4 = base spawn, 5 = library site. |
| `lane` | integer | 1 top, 2 center, 3 bottom. **0** if the node belongs to no lane — connectors and base interiors. |
| `milestone` | integer | 0–8 if this node is a milestone; **0** otherwise. Read together with `kind`, never alone. |
| `team` | integer | 0 neutral, 1, or 2. Which half of the field the node sits in. |
| `neighbour` | integer[] | Node ids reachable in one step. Length 2 for plain lane points, 3 for junctions. |
| `structure` | integer | Id of the tower or library standing here, or **0** for none. |

There are no nil fields anywhere in this structure. A node with no structure
stores the integer zero, not an absent value. A nil check is a question about
whether the map builder did its job, and that question belongs in the map
validator, not in the movement loop that runs a thousand times a tick.

### lane

| Field | Type | Meaning |
| --- | --- | --- |
| `id` | integer | 1, 2, or 3. |
| `path` | integer[] | Node ids in order from team 1's library to team 2's library. |
| `milestone_node` | integer[9] | Node id for each milestone index 0–8. |
| `junction` | integer[] | Node ids on this lane that carry a sign-post. Empty for the center lane. |
| `length` | double | Total path length in paces. Cached because the renderer wants it constantly. |
| `width` | double | How many paces across. The center lane's is greater. Feeds the frontline queue and the renderer, nothing else. |

### How a soldier uses it

A soldier stores `lane`, `node_from`, `node_to`, and `progress` (a double from 0
to 1). Advancing is: add speed × tick to `progress`; if it passes 1, set
`node_from = node_to`, look up the next node along the lane's path in the
direction the soldier is travelling, and carry the remainder. At a junction, the
soldier asks the sign-post standing there which neighbour to take — see
[sign-posts and lane routing](013-signposts-and-lane-routing.md). Ordinary wave
units ignore sign-posts entirely and always continue along their own lane.

## What this document does not decide

The exact field size, the spacing between milestones, the connector length, and
whether the field is square or rectangular are balance values, not design values.
They live in the map builder's parameter table and are reported by the map
validator; do not copy them into prose here, because they will change and this
page will not.
