**Setup:** the house setup script laid out the usual folders (docs, notes, src,
issues, the RAM-backed `tmp/` and the phase-demo picker). I moved `vision` into
`notes/vision`. The report is in `docs/scoring-options.md` and listed in the

**The report in brief.** Each option measures "used by future commits"
differently. They're ordered from most likely to work well to most unusual:

1. **Survival:** how many of the lines a commit wrote are still alive in the
   newest commit (git blame credits each line to the commit that last wrote it).
   This rewards foundations. It gives nothing to code that was used for months
   and then rewritten. A full pass over the monorepo takes about 40 minutes on
   one thread, or a few minutes spread across all cores.
2. **Name references:** pull out the names a commit defined (functions,
   modules), then count how many later commits mention them. This is the closest
   match to your vision's "code uses came from those pieces of machinery". Short
   names like `init` match everywhere, so they'd need filtering.
3. **Built-upon regions:** walk forward through the history and track who owns
   each line. When a later change lands next to a commit's lines without
   deleting them, that commit gains a point. This separates "kept breaking" from
   "everything new grew from it". It's the most work to write.
4. **Later touches:** count later commits that changed the same files. It's
   cheap (20 seconds for a year of the monorepo), but it measures attention, not
   use. Code that breaks every week would glow, so pruning the dark spots might
   remove stable code.
5. **Require graph:** a file gains credit when later files load it (`require`,
   `source`, `#include`). The meaning is clear, but it only works at the level
   of whole files.

**One thing I found that affects every option:** in the monorepo, the
conversation transcripts are huge and almost never deleted. Under option 1 they
would score as the best code ever written and drown out everything else. So
every option needs a list of folders and file types to leave out.

**Questions for you** (all five are also at the end of the report):

1. **Why does a square glow?** When you look back at a day and think "that was
   good work", what made it good? Was it that the code is still there, that
   other code calls it, or that later work grew around it? Your answer picks
   between options 1, 2 and 3.
2. **One commit on a quiet day:** if a day had a single excellent commit, should

3. **What's left out:** transcripts, generated HTML and images are the obvious

4. **How long a future:** does each commit get scored on everything since, or

   always look bright, because nothing has had time to replace them yet.
5. **The screenshots:** should `1.png` and `2.png` move into `notes/` beside the
