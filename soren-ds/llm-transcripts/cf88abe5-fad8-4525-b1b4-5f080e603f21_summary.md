## What's wrong

was inherited from the project's hardware overview, where it's documented as the

- u-boot copies the bytes into RAM at `0x0200_0000`

- u-boot jumps to `0x0200_0000`

- The first two instructions (the NOP and the branch into `_start`) work fine because they're encoded as offsets relative to where the CPU is currently fetching from — they don't care about the linker's opinion

don't crash. MMIO writes also work, because hardware register addresses are
absolute physical addresses. But every absolute address the linker resolved at

### User Request 16

what's the difference between PWM and GPIO?


--------------------------------------------------------------------------------

### Assistant Response 16

Both are ways the chip drives a single physical wire that exits the chip and
goes somewhere — an LED's anode, a motor's input, a speaker's terminal, a
sensor's signal line. They differ in what they put on the wire.


**GPIO** — "general-purpose input/output." The chip has a small controller block that can do exactly three things to the wire: drive it to the chip's logic-high voltage (about 3.3 volts on this device), drive it to ground (zero volts), or stop driving and let the chip read what voltage some external thing is putting on the wire. Software writes a "1" or "0" into a register inside the controller; the controller flips a tiny transistor that connects the pin to either the 3.3-volt rail or the ground rail. Output is binary — on, or off, nothing in between. For an LED, GPIO-high = lit at full brightness, GPIO-low = dark.


**PWM** — "pulse-width modulation." A different controller in the chip drives the same kind of pin, but instead of holding the pin steady, it toggles between high and low very rapidly — typically thousands or millions of times per second. Each cycle of toggling has a "duty cycle," meaning what fraction of the cycle is spent at high. Twenty-percent duty means the pin sits at 3.3 volts for 20% of every cycle and at ground for the other 80%. The toggling is so fast that most things on the other end of the wire can't keep up with it and just see the average: an LED looks like it's lit at twenty-percent brightness rather than blinking visibly, a small motor spins at twenty-percent of its top speed, a speaker emits a quiet hum rather than audible clicks. Software writes the duty value into a register and the controller does all the high-frequency toggling itself in dedicated counter hardware.


**Why have both.** GPIO is cheap hardware — a single transistor and a single register bit per pin. PWM is more hardware — a counter, a comparator, a duty register, a period register — but it lets you smoothly control brightness, motor speed, or sound intensity without needing an external analog circuit to convert digital values into a varying voltage. If a wire only needs on/off, GPIO is fine. If it needs fades, dimming, or smooth ramps, PWM earns its keep.


**The wire is the same wire.** What changes between "this pin is GPIO" and "this pin is PWM" is which controller inside the chip is listening to your register writes and operating the transistor at the pin's far end. The pin-multiplexer setting we've been worrying about is exactly the register that picks which controller owns a given pin. Function zero in the pin-mux = the GPIO controller is in charge; function one = the PWM controller is in charge; functions two through fifteen would route the same wire to other peripherals the chip can multiplex onto the same pin (a UART transmit line, an I²C clock, etc.).


**For our situation.** We have GPIO confirmed working. We don't have PWM working, and getting it working requires another round of investigating which clock-gate register controls the PWM1 controller and writing the right pin-mux value to route the pins back to function one. For boot stage signaling — which is the whole reason the LED layer exists right now — we only need on/off. Dropping PWM entirely and driving the LEDs as GPIOs from the LED layer is a legitimate phase-1 simplification: we lose the smooth-fade breathing heartbeat (the amber LED that was supposed to slowly pulse during the multi-minute eMMC backup), but we get a reliable LED layer that works today and a single peripheral less to chase. The breathing heartbeat can come back later, once we have a debug channel up that makes the next PWM-bringup attempt less of a flying-blind exercise.


Worth considering whether to take that simplification before sinking more time
into PWM.

The aarch64 CPU has two "personalities" of registers: the integer side (which

2. C entry paints the hello flash (two amber, about a second)

3. C entry paints green for the kernel-reached-main stage

4. Allocator self-test starts running, calls into the page-allocator function

5. First SIMD instruction inside the page-allocator function fires a trap

bootloader's handler decides the right thing to do with an unexpected trap is
reset the system.

7. Bootloader re-runs, kernel re-runs, back to step 2.

Not weird at all, and not inefficient for what we're actually doing. It's a

frequently ban it outright. The original Game Boy, the DS, the PlayStation 1 all

**What "disable floating point" actually means at the language and compiler level**


There are two separate things to think about:


- *The hardware FP/SIMD unit on the chip.* This is the dedicated math co-processor we've been tripping over. We can tell the compiler "never emit instructions that touch that unit" (the flag we discussed). The kernel never enables the unit, so the hardware stays off, and any instruction that would have touched it doesn't exist in our binary.

- *The C language's `float` and `double` types.* These are language-level concepts. When the compiler sees `float a = 3.14;` in source, it normally translates the math into instructions that touch the FP unit. Without the FP unit, the compiler has two options: emit calls to a software floating-point library (which we don't link because we're freestanding), or refuse to compile the code at all.


When you add the flag we discussed, the compiler also stops accepting `float`
and `double` types in any code it compiles for us. Any attempt to do `float a =

hardware-level ban. The C source you write is integer-only; if you try to use
floats, the build refuses.


**What we lose by not having floating point**


The class of things that naturally want floating-point: physics, smooth
animation curves, 3D rotations, audio synthesis with continuous pitch control,
color blending with smooth gradients, signal processing. Any algorithm whose
natural expression involves "this quantity changes continuously over time and I
need to interpolate between values."


We can do *all* of those things without floating-point. The technique is called
fixed-point math: pick a power of two (say 65536), and represent the fractional
number 1.5 as the integer 1.5 × 65536 = 98304. Multiplication, addition,
subtraction work the same as on integers; division and the like need a one-line
correction to keep the scale factor right. Functions like sine, cosine, square
root are implemented as lookup tables or with iterative integer algorithms. The
math is exactly as fast as integer math (because it *is* integer math), and the
precision is set by the scale factor — 16 bits of fractional precision at
scale 65536, more if you go bigger.


The PlayStation 1's entire 3D engine ran in fixed-point. The DS's GPU works in
fixed-point. The cost is "a little more careful when you write the math" in
exchange for "everything is one register class, no save/restore on context
switches, no traps to worry about, no floating-point precision quirks like NaN
or rounding modes." For game logic on this device, fixed-point is honestly often
the better fit.

- The current bug goes away. The compiler stops emitting the instructions that trap.

- One less hardware subsystem the kernel has to be aware of. If we eventually add multi-threading, threads don't need to save and restore the FP register file on every context switch — the FP register file isn't in play at all.

- One less category of bug. Floating-point on aarch64 has subtle behaviors around denormals, rounding modes, and NaN propagation that we don't have to think about.

- Smaller binaries (the FP code paths the compiler would have emitted just aren't there).

### Assistant Response 23

The naming is genuinely confusing — let me untangle it.


**What "multiple data" actually refers to**


A normal CPU register on this chip holds one 64-bit integer. An instruction like
"add register A to register B" takes those two 64-bit integers and produces one
64-bit answer. One operation, one piece of work.


A SIMD register on this chip is much wider — 128 bits. But it doesn't hold
*one* 128-bit value (usually). Instead, the hardware divides it into "lanes":


- Sixteen lanes of 8 bits each, or

- Eight lanes of 16 bits, or

- Four lanes of 32 bits, or

- Two lanes of 64 bits.


A SIMD instruction operates on every lane in parallel. "Add SIMD register A to
SIMD register B with four-lane mode" means: take lane zero of A, add lane zero
of B, store the sum in lane zero of the result; do the same for lanes one, two,
and three; all in one cycle. One instruction, four (or eight, or sixteen) pieces
of work simultaneously.


That's where "multiple data" comes from — the multiple data is the multiple
lanes packed into the single wide register. One instruction acts on all of them
at once. The classification term for this is in Flynn's taxonomy: SISD is a
normal CPU (one instruction, one piece of data), SIMD is this packed-lane setup,
MIMD is what multiple cores running independently look like.


So "single instruction, multiple data" is about how *one instruction* processes
*multiple lanes in one register at one point in time*. It's a way of doing more
arithmetic per cycle on a single core.


**No, you don't have to use floats with it**


The lanes can hold integers or floating-point values. The SIMD hardware unit
supports both. Most of the SIMD-style optimizations the compiler was emitting in
our kernel were *integer* — using a 128-bit register to zero out sixteen bytes
of memory in one store, faster than two stores of eight bytes each. The compiler
emitted floating-point-flavored instructions sometimes too, but the data it was
operating on was integer memory; it just used a register that happens to be
capable of floats for the data move.


The reason "FP" and "SIMD" get conflated on this chip family in particular is
that they share the same hardware unit. The 32 wide registers are used by both
floating-point math and SIMD lane math; one control bit at the CPU's exception
level enables both at once. There's no way to have "SIMD on, FP off" or vice
versa — they're entangled at the hardware level. So when people say "disable
FP" on this architecture, they mean "disable the whole 128-bit wide register
file," which catches both kinds of use.


**The threading concern is real and is a separate question**


Your read is sharp. The SIMD register file is held in the CPU, not shared
between threads — but in the same way the integer register file is held in the
CPU and not shared between threads. Both have to be saved out to RAM when one
thread yields and another takes over, and restored back into the CPU when the
original thread resumes.


The difference is just bookkeeping. The integer registers are 32 of them × 64
bits = 256 bytes per thread. The SIMD/FP registers are 32 of them × 128 bits =
512 bytes per thread. Plus a few control registers. So a thread that uses both
has about 800 bytes of register state the scheduler has to save on every yield.


There are three threading dispositions a kernel can take with respect to
SIMD/FP:


- *Disabled entirely.* The hardware is off, the compiler emits no SIMD instructions, threads don't have an FP/SIMD register state because nobody touches that register file. Save/restore is just the integer registers. Simple.

- *Enabled, eager save.* The hardware is on, threads can use SIMD, and the scheduler unconditionally saves and restores the SIMD register file on every yield. Costs the extra bookkeeping every time. Simple and predictable.

- *Enabled, lazy save.* The hardware is on, but the scheduler marks the SIMD register file "untouched" when a thread starts running. The first SIMD instruction the thread executes faults; the fault handler saves the previous thread's SIMD state (if any) and clears the mark, then re-runs the instruction. Threads that never touch SIMD pay zero cost. Threads that do touch SIMD pay the save once. This is what the Linux kernel does. More code, more clever, more failure modes if you get it wrong.


A multi-threaded kernel that wants SIMD to be usable picks one of the second
two. Soramech, when it lands, will need to commit to one of these. The choice
isn't tied to whether the threading system exists; it's tied to whether you want
SIMD to be available.


**Where I'd suggest landing**


For phase 1, where we have no soramech yet and no thread state to save anyway,
the simplest move is option one — disabled entirely. The compiler doesn't emit
SIMD instructions, the hardware unit stays off, and the current trap-and-reset
cycle goes away. When soramech arrives and threading becomes a first-class
concept, that's the moment to revisit: if soramech is a coroutine system where
yields are explicit, the scheduler can save the SIMD register file at yield
points (option two, eager save), and threads can then use SIMD freely. If
soramech is preemptive, eager save still works fine; lazy save is an
optimization to consider once we measure that most threads don't touch SIMD.


The SIMD register file is a real piece of hardware sitting unused at the moment,
and turning it on is essentially free once the bookkeeping is in place. The
question is *when* to do the bookkeeping. My read is that doing it now (without
a threading system designed) would be premature; doing it as part of soramech
(where the scheduler can be built with FP-aware save/restore from day one) is
the right moment.


So my recommendation stands — disable FP/SIMD for phase 1, with the explicit
understanding that soramech's design will decide whether to bring it back. Want
to proceed?

### Assistant Response 25

You caught a real subtlety. Let me untangle it.


**The clobbering happens within a single core, not between cores**


Each core has its own register file. Two threads running on *different cores*
never see each other's registers — those are literally different transistors
in different parts of the chip. Threads on different cores can both use SIMD
freely and never collide.


The trouble starts when *two threads share a single core through time-sharing*.
That's the standard arrangement when you have more threads in the system than
you have cores. If we have four cores and we want, say, sixteen logical threads
in flight (game logic, audio mixer, physics, network, file I/O, half a dozen
background entities, etc.), each core has to take turns running four of them.


While a thread is running on a core, it owns that core's complete register file
— both integer and SIMD. The other three threads sharing that core are
suspended, with no presence in the core at all. When the scheduler decides it's
time to switch from thread A to thread B on the same core, thread B walks into a
register file still holding thread A's last values. If thread B starts writing
into the SIMD registers, it overwrites what thread A had there. Without
intervention, when thread A's turn comes around again, the values it stored
before its turn ended are gone — replaced by whatever thread B did.


The "intervention" is the save-and-restore step. Before the scheduler hands the
core to thread B, it copies thread A's entire register file (integer registers,
SIMD registers, control registers) into a chunk of memory that belongs to thread
A. Then it copies thread B's register file out of *its* memory back into the
core. Now thread B starts with its own values; thread A's are sitting safely in
memory until thread A's next turn, when they get loaded back.


This is true for integer registers too — it's not a SIMD-specific thing at
all. Every time-sharing kernel since the 1970s has done this dance with integer
registers. SIMD just adds more bytes to the save-and-restore cost (an extra 512
bytes per thread on this chip on top of the 256 bytes of integer state).


**What this means for the "do threads ever clobber each other's SIMD" question**


Three regimes, and they have very different costs:


- *Threads on different cores.* No clobbering, ever. Each core's SIMD unit is private to that core. No bookkeeping needed for cross-core protection — the chip's geometry handles it.

- *Threads on the same core, no time-sharing.* If we design the system so each core has exactly one thread pinned to it and that thread never yields, there's also no clobbering — the one thread on the core owns the register file forever. No save/restore needed because there's nothing to switch to.

- *Threads on the same core, time-sharing.* This is where the scheduler has to save and restore SIMD state on every switch. The cost is the 512 bytes of register state plus the cycles to copy them.


Soramech's design will pick a posture. "One pinned thread per core" is the
simplest and fastest but caps the total parallelism at four — which is fine
for some designs and limiting for others. "Many threads, time-sliced per core"
is more flexible but pays the save-restore cost. A hybrid where some cores have
a fixed pinned thread and others time-share is also possible.


**The take-away for the SIMD-enable decision**


When soramech turns SIMD on, the eager-save policy you picked means "every
context switch on every core saves and restores 512 bytes of SIMD state." That's
pure scheduler bookkeeping that pays for the freedom to let any thread use SIMD
without worrying about it. Lazy save would defer the cost until a thread
actually touches SIMD — many threads in a typical system never do, so most
save/restore work goes away — at the cost of an unpredictable trap-and-fixup
path in the scheduler. The choice you locked in (eager) trades a little
throughput for predictable timing, which is the right trade for a system that
wants tight control over scheduler latency.

### Assistant Response 29

Three things first, then I'll write the docs and issue files.


**What the watchdog actually does**


A watchdog is a piece of hardware whose only job is to reset the chip if the
software running on the chip stops checking in. The mechanism is just a
countdown timer. The hardware gets configured at boot with a timeout value,
starts counting down from that value, and if it reaches zero without software
writing a specific "I'm still here" value to a specific register, the watchdog
drives the chip's reset line and the whole system reboots. The countdown clock
is usually the chip's slow always-on oscillator (the 24 MHz crystal on this
chip), divided down to keep the count manageable.


The point is recovery from software hangs that would otherwise require physical
intervention. If a deployed device's main software gets stuck — a bad pointer,
a missed interrupt, an infinite loop, a peripheral that never returns — the
watchdog notices that nobody is checking in anymore, resets the chip, and the
device starts over. That's much better than a dead device that needs a human to
power-cycle it.


In our specific case the watchdog is hostile to development because we're not
running anything that pets it, but the watchdog itself is doing exactly what it
should. The fix for phase 1 is to silence it (so the kernel has room to
misbehave for hours at a time while we debug); the fix for a shipping product is
to do what the watchdog was designed for, which is to feed it from a
known-trustworthy source so it resets the device only when the software has
actually hung.


**The soramech petting task is the right end state**


Once soramech is running with periodic task support, a dedicated petting task is
the canonical pattern — and the same pattern is what Linux does, what every
embedded RTOS does, and what the watchdog's hardware design assumes. The task
would be a few lines: every N milliseconds, write the byte value 0x76 to the
watchdog's restart register. If the rest of the kernel ever hangs in a way that
prevents soramech's scheduler from reaching this task, the writes stop, the
countdown hits zero, the chip resets. Recovery for free.


There's a subtler discipline that goes with this: the petting task shouldn't pet
faster than its own scheduler runs. If you pet from a hardware interrupt that
fires regardless of scheduler state, the watchdog never catches a scheduler-side
hang. The right place is from a normal scheduled task at the lowest priority —
if the scheduler can't get around to running a low-priority task, the system is
sick enough that a reset is the right move.


**Hardware sources of periodicity on this chip**


Things the silicon gives us for free, no software construction needed:


- *ARM Generic Timer.* The biggest one and the most underrated. Every aarch64 CPU core has a built-in 64-bit counter and a comparator pair, accessible through system registers (the same kind of register the kernel's been using to mask exceptions and install the vector table). The counter is shared across all cores at the system level — every core reads the same monotonically-increasing tick. The frequency is fixed at boot; on this chip family it's the 24 MHz crystal divided down to typically 24 MHz exactly, exposed through a read-only system register. The comparator pair lets each core schedule an interrupt at a specific tick value — set the comparator, enable the timer, when the count reaches the comparator the interrupt fires. This is what every modern aarch64 kernel uses for scheduler ticks, sleep timeouts, and time-of-day. It's free, it's per-core, it has no MMIO surface, and it's the standard answer.

- *Hardware Timer blocks at MMIO.* The chip exposes a handful of dedicated timer peripherals at specific MMIO addresses (the device tree calls them `timer@fe5f0000` and friends). Each one is a configurable counter with reload and interrupt-on-zero capabilities. These are leftover from before ARM standardized the Generic Timer — useful for systems with the Generic Timer already busy on something else, or for cases where the Generic Timer's resolution isn't enough. Phase 1 doesn't need them.

- *PWM controllers as timers.* This is the underappreciated one. The same hardware blocks that drive the LEDs through their duty-cycle output can also be configured as plain interrupt-on-period timers. The chip has many PWM channels; the ones not used for LEDs are just sitting idle, available to be programmed as timers. They're slower to set up than the Generic Timer (more MMIO to write, clock to ungate, pinmux concern — though if you're not using the output pin the pinmux doesn't matter), but they're a real second timer if you need one.

- *Real-Time Clock.* The chip has a true RTC at a specific MMIO address, backed by its own oscillator and (in the deployed device's case) by a small battery so it keeps wall-clock time through power-off. The RTC counts in seconds typically, with finer subdivision available through its registers. Different purpose from the Generic Timer — the Generic Timer measures elapsed cycles since boot, the RTC measures elapsed seconds since 1970. Useful for timestamping log entries, less useful for scheduler ticks.

- *Performance Monitoring Unit counters.* Each core has dedicated counters for events like cycles executed, instructions retired, cache misses, branch mispredictions. Programmable as event counters with overflow interrupts. Mostly used for profiling rather than scheduling, but they're a periodic source if you want one.


For our soramech-side watchdog petting task, the right answer is the ARM Generic
Timer — it's universally available, has no peripheral bring-up cost, and gives
us the kind of precise low-overhead periodic interrupt scheduling that a
scheduler tick wants.
