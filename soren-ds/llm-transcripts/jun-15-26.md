End-to-end, the story has three acts: the development machine produces a
bootable image, a dedicated USB drive carries that image across an air gap to a
quarantined laptop, the laptop writes it to a microSD card, and the card hands
the device's boot ROM a sequence of bytes it recognizes well enough to walk all
the way to our kernel.


## Act 1 — Building the image on the dev machine


**1. Compile.** `./scripts/build` invokes the Makefile, which walks `src/` for every `.c` and `.s` file, compiles each with the aarch64-elf cross-toolchain into `tmp/build/kernel/`, and links them under `src/kernel.ld`. The linker pins three regions in order at the load address (`0x00280000`): a 64-byte recognition envelope, the kernel's code section with `_start` at its top, and the exception-vector table on a 2 KB boundary further out. Object files stay in RAM-backed `tmp/`; the SSD never sees them.


**2. Extract the kernel image.** Make runs `objcopy -O binary` on the linked ELF, peeling off all the ELF wrapping and writing the raw bytes between the load address and the end of `.bss` to `output/kernel.img`. The result is ~15 KB whose first byte is a NOP, byte 4 is a branch to byte 64, byte 56 is the four-byte `ARM\x64` magic the bootloader scans for, and byte 64 is the first instruction of our boot code.


**3. Assemble the bootable image.** `./scripts/build-bootable-sd`:

- Re-checks each of the three durable blobs in `libs/sd-image-parts/` against its committed `.sha256` (catches tampering or accidental edits before they propagate).

- Allocates a 272 MiB zero-filled file at `output/bootable-sd.img`.

- Writes an MBR partition table at sector 0 with one bootable FAT32-LBA partition starting at sector 32768.

- Drops the Rockchip idbloader (the borrowed RKNS-magic blob holding DRAM init and a small loader) into the unpartitioned gap at sector 64.

- Drops the u-boot FIT (the borrowed `d00dfeed`-magic blob holding u-boot proper plus the secure-world firmware) at sector 16384.

- Builds a 256 MiB FAT32 image with `mkfs.fat`, labels it `ROCKNIX`, and populates it with three files: our kernel as `/KERNEL`, the borrowed device tree as `/device_trees/rk3568-anbernic-rg-ds.dtb`, and a four-line `extlinux.conf` pointing u-boot at the kernel and the tree.

What lands at `output/bootable-sd.img` is a single 272 MiB file whose layout
matches a known-working community image byte-for-byte in the pre-partition
region, and whose partition holds only the files we want loaded.

**7. BootROM.** The RK3568's mask ROM is the first code that runs. It looks at the SD card for a Rockchip-format idbloader at sector 64 — which is exactly what we put there. The idbloader's `RKNS` magic signals "I'm yours to run." BootROM loads it into the chip's small on-chip SRAM and jumps to it.


**8. DRAM and the miniloader.** The idbloader contains Rockchip's DRAM initialization code — without which nothing larger than that on-chip SRAM is usable — followed by a small loader (the "miniloader" or SPL). DRAM comes alive; the miniloader reads sector 16384 (the byte offset the convention pins) to find the u-boot FIT, copies it into the now-usable DRAM, and jumps to it.


**9. Secure world setup.** The FIT image's TF-A (Trusted Firmware-A, BL31) sets up the secure-world plumbing the chip's architecture expects to exist before non-secure code can run cleanly. Then it hands control to u-boot proper.


**10. u-boot scans for a boot source.** u-boot's `distro_bootcmd` (the standard boot-discovery script baked into community u-boot builds) walks the configured block devices, looks for partitions marked bootable in the MBR, finds our FAT32 partition labelled `ROCKNIX`, and reads `/extlinux/extlinux.conf` from it.


**11. extlinux loads our kernel.** The config tells u-boot: load `/KERNEL` into RAM at `kernel_addr_r` (which on RK356x boards is `0x00280000`), load `/device_trees/rk3568-anbernic-rg-ds.dtb` at `fdt_addr_r`, then call `booti`.


**12. The recognition check.** `booti` reads byte 56 of the loaded image, sees `ARM\x64`, and decides it's a kernel it will accept. It reads the image-size field (so it knows how much RAM the image needs counting BSS), reads the flags (which say "leave me where you loaded me, I'm flexible"), and jumps to byte 0 of the image.


**13. The two header instructions.** Byte 0 is the NOP — it executes harmlessly. Byte 4 is the branch — it jumps to byte 64. That's the only work the recognition envelope ever does at runtime.


**14. **15. The kernel runs.** From `kernel_main` onward, everything is our own code: PWM bring-up, LED stage signaling, USB controller initialization, eMMC dump, debug log to SD card — whatever the kernel proper is configured to do.

After `booti` jumps to byte 0 and the NOP-then-branch falls into `_start` at

## Boot code prep (in 001-boot.s)


**The first dozen instructions.** `_start` masks all four asynchronous-exception sources (debug, SError, IRQ, FIQ) so a stray interrupt cannot fly out of nowhere before handlers exist. It then sets the stack pointer to the top of a 16 KB region the linker reserves at the high end of the loaded image — without this, every C function call would push registers into wherever the stack pointer happened to wake up at, which is undefined. It zeroes the `.bss` region eight bytes at a time between two linker-defined symbols, so C statics with no initializer come up as zero per the C standard. It installs the exception vector table by writing the table's base address into `VBAR_EL1`, so any future synchronous fault (bad pointer, illegal instruction) routes through the panic handler instead of executing whatever byte happens to live at the architecture's default vector base. Then it calls into the C entry, `kernel_main`.


## kernel_main, in order


**1. The LEDs come up first.** Three RK3568 PWM channels (5, 6, 7) get configured with a chosen frequency, then duty cycles get assigned to the green, amber, and red LEDs to encode an integer "stage" the developer can read by glancing at the device. The first stage written is `STAGE_KERNEL_MAIN`, which means "we got this far." From here on, any fatal failure changes the LED pattern to the panic code, so a developer with no other tools can decode "we got past stage X but died before stage Y." The LED-code table lives at `docs/015-led-diagnostic-codes.md`.


**2. The page allocator wakes up and self-tests.** A one-bit-per-page bitmap gets carved out of the bottom of the kernel's memory pool, marking the bitmap's own pages as in-use. A small self-test allocates a handful of pages, checks they are distinct and page-aligned, frees them, and confirms the freed pages get reused. If any of that math fails, the call doesn't return; the panic LED lights and the core parks. No one is asking for pages yet, but later subsystems will, and getting this confirmed early means a memory bug shows up as "allocator self-test failed" rather than as a random misbehavior somewhere downstream.


**3. The USB controller comes up in device mode.** The USB 2.0 PHY gets brought out of suspend through the chip's general-purpose configuration registers, the DWC3 controller gets soft-reset, the port direction is pinned to "device" (so we look like a USB peripheral to a host laptop, not like a host ourselves), and the chip's identification register gets read back to confirm the controller is alive — the value should be a specific Synopsys magic. On success the LED stage advances to `STAGE_USB_CONTROLLER`; on mismatch we panic, because if the controller doesn't even identify, no amount of later code can fix it.


**4. Endpoint-zero plumbing gets configured.** Descriptor tables for the device, the configuration, the interfaces, and the strings get pinned in `.rodata`. A setup-packet dispatcher table maps standard USB requests to the responses the host will see during enumeration. The DWC3's endpoint-zero hardware gets configured through its command interface (the DEPSTARTCFG / DEPCFG / DEPXFERCFG sequence). When this returns, the chip is ready for the host to drive bus reset and start asking us what we are. The actual transfer-ring plumbing that turns dispatched responses into bytes on the wire runs in `usb_poll`, which we don't reach yet.


**5. The eMMC controller comes up.** The RK3568's dedicated SDHCI host (separate from the SD/MMC controllers below) gets initialized. The JEDEC eMMC identification sequence walks card states from idle through ready through identification through stand-by through transfer (CMD0, CMD1, CMD2, CMD3, CMD7 in the eMMC spec). After this returns, the kernel can read or write single 512-byte blocks on the internal eMMC through CMD17 and CMD24 — the foundation for everything downstream that wants to look at what Anbernic shipped.


**6. The microSD controller comes up.** The RK3568's SDMMC0 controller — a different IP block from the SDHCI on the eMMC, namely Synopsys's DesignWare MSHC — gets initialized through a different bring-up path. The SD spec's card-init dance walks CMD0, CMD8, the ACMD41 loop until the card is ready, CMD2, CMD3, CMD9, CMD7. Single-block read and write through CMD17 and CMD24 work after this, against the inserted microSD.


**7. The SD-card-backed debug log comes online.** A ring buffer in DRAM holds debug text; a flush routine periodically copies the ring's contents to a reserved region of the microSD card (well above where the BootROM looks, so the card stays bootable). The kernel's `debug_write` function — the one the USB CDC-ACM channel will eventually expose to a host — now also appends to this ring on every call. So even with no host computer attached and no USB cable plugged in, the kernel's narration of its own bring-up gets persisted to the SD card for later inspection.


**8. The whole eMMC gets copied onto the microSD card.** This is the payload step of phase 1. The eMMC's 32 GB of contents — that's 67,108,864 sectors of 512 bytes — gets read sector by sector through the eMMC driver and written into a reserved region of the microSD card starting at SD LBA `0x200000` (about 1 GB into the card, well clear of the boot chain at the bottom). The reserved region is 32 GB of SD space, so the developer's microSD needs to be at least ~33 GB. While this runs, the LED stays at `STAGE_USB_ENUMERATED` and the debug log fills with progress narration; if any sector read or write fails, the log gets flushed, the panic LED lights, and the core parks so the partial dump is preserved.


**9. Final log flush + success stage.** Once the backup completes, the debug log gets one more flush to make sure the bring-up narration is on the card before the developer powers off, and the LED advances to `STAGE_BACKUP_COMPLETE` — the green "we're done" signal.


**10. The polling loop.** The kernel drops into a `while(1)` that calls `usb_poll`. That function walks the USB event ring, distinguishes endpoint events from device events, drives the four-stage control-transfer state machine that turns the descriptor tables from step 4 into actual responses, handles bus reset (which resets the state machine and re-arms endpoint zero), and applies `SET_ADDRESS` to the controller's `DCFG` register when the host issues it. If a host laptop happens to be plugged in with a USB cable, the laptop's `lsusb` reports our device at this point, and the CDC-ACM channel becomes a virtual serial port the laptop can read with `cat /dev/ttyACM0` to see the same debug text that's already on the SD card.


The kernel does no display work (the bottom and top screens stay dark — issues
111a-d will change that), does no networking, and does not yet flash itself to
the eMMC's boot partition (`110b`'s writer exists, but the call to it is
commented out in `kernel_main` until `110e`'s real-LBA-of-the-boot-partition
step closes — writing the wrong LBA would land bytes on top of u-boot itself,
which is the hard-brick path the safety doc names by name).


## What you do next, with the card in hand

`dd` two ranges off it:

- The reserved debug-log region (small, plain-text-ish): tells you whether each bring-up step reported success.

- The reserved eMMC-mirror region (32 GB): a byte-for-byte copy of what Anbernic shipped.
