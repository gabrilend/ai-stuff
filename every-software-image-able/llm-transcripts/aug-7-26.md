**What I built.** Two new pieces of assembly. The first builds the tokenizer's
four lookup tables — which token says each byte, what each merge rule
produces, where each token's text lies, and the text itself — out of the
word-lists the model carries, using no hash, no strings, and no memory but a run
it was handed. This was a piece nobody had listed: the engine's think-time half
was written never to touch a string precisely so something else would pay that
cost once at startup, and the something else was still host code. The second is
the loop, which calls everything through a pointer held in a plan, because there
is no linker and a call written by name is a note for a linker — a dropped
note leaves a zero, and a call with offset zero is a call to itself, which is
two of the four silences this project has already met.


The loop's control flow copies the readable loop's exactly: length checked
before drawing, the finish token checked after drawing and not kept, the room
checked after keeping and before thinking. That ordering is the specification,
not a style — each decides whether one more word is drawn, and one different
word means two different conversations from there on.

**Two open questions I could not resolve from the documents, both now recorded
in the open-questions document and in the ticket.** I need your call on the
first before the image builder can close:


1. **How does a driver find the image's regions on a real card?** The builder
   lays down five regions on a raw medium at block boundaries. Every board here
   boots through UEFI, where firmware opens *one file* and hands over a pointer
   to its contents — the other four regions are not at a knowable distance
   from anything the driver can see. I carried the model, text and randomness
   inside the payload (64 KB past its own first instruction, reached by
   measuring from where it stands), which works and is what the memory-report
   payload already does. But a hundred-megabyte model should be read as needed,
   not loaded whole. The alternative is the machine opening the medium it booted
   from — a storage driver, which your ticket assigns to the machine rather
   than the seed, on the grounds that its failure is a wrong answer rather than
   silence. That reasoning holds, and it leaves a gap: the machine can't write a
   storage driver until it can think, and it can't think until it's read the
   regions.


2. **Is the word-table preparation paid at every boot or baked in by the
   builder?** Resolving one merge rule means walking the vocabulary comparing
   bytes. On the fixture that's nothing; on a real model with thirty thousand of
   each it's tens of billions of comparisons before the first word. The blob
   format's own note says "read once at startup," which settles it for now —
   but that sentence was written before anyone counted. Nobody has measured it
   on a real model, and I think the honest answer is that it shouldn't be
   decided until someone has.
