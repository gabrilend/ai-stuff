## What mini-AGI actually is

A byte-level language model in Python, trained from scratch on one 8 GB consumer
GPU, that never stops training. Three mechanisms matter:

- **The recurrent trunk.** Two dense blocks read incoming bytes, then one block
  is applied up to 24 times in a row. Each application picks its own top-8
  experts out of a shared pool, so the same block does different work on each
  pass.
- **The halting head.** A scorer looks at every character on every pass and
  stops that character as soon as another pass would not change the answer.
  Cheap characters exit early; hard ones keep circulating. Depth is decided by
  the data, not by the architecture.
- **The two learning rates.** The shared trunk moves at one tenth the rate of
  the experts. New data lands mostly in the experts; the part everything depends
  on barely drifts. That is their claimed defence against forgetting what it
  already knew.

Experts live on disk and are paged into a 32-expert working set on the GPU, so
the model can be larger than the card.

## every-software-image-able — the tightest relation

Your image-able design lists three things that ride on the flashed chip: the

## minimal-soramech — the substrate, and a structural echo

Your image-able project already names soramech twice. The mind document lists
"the ceramic platform" among the build patterns riding on the chip alongside
dispatch tables, thread pools and looping iterators, and the deferred note parks
it with *"it should be described before it is referred to again."* So soramech
is the recommended answer to *what is a unit of running software* on a machine
that has to invent its own answer.

The echo with mini-AGI is real and not just thematic. Soramech's rule is that a
station runs when and only when every one of its input ports holds a value, and
its two box types are a **comparator** (route the result to a destination chosen
by a comparison) and an **iterator** (send to target one, then two, then three,
then wrap). Now look at mini-AGI's core: a block applied repeatedly with a
data-dependent trip count, a halting score deciding per character whether to
route onward or exit, and a top-8-of-pool selection that is a routing decision
made fresh on every pass. That is a soramech map — an iterator around a block,
with comparators deciding exit and destination. Mixture-of-experts routing *is*
dataflow with dynamic wiring.

And your image-able line "nothing here is single-threaded if it does not have to
be" is soramech's single rule restated. If that machine ever rebuilt its own
mind from scratch, soramech is the engine it would build it in, and mini-AGI is
the closest published description of what it would build.

## r-mail — the guard against a failure you already wrote down

Your deferred note parks *mail between machines*: network messaging "built into
every system as fine-tuning on the suggested models." You recorded the hazard
yourself — the wire format would live in the weights rather than in a
document, both ends being models means they can agree without a specification,
and neither can **check** that they agree because there is no third thing to
validate against. Two differently-tuned machines drift silently instead of
failing loudly.

r-mail is that third thing, already built. The format is a plain text file whose
name is the subject and whose `to:` lines are the routing. The protocol is a
written document. Consent is explicit and manual — the recipient gets a file
stating the filename, expected size, free space and space remaining after, and
deletes one of two lines to answer. Deletion propagates in both directions, and
removing one `to:` line deletes exactly one recipient's copy. None of that lives
in a model's weights, so a mismatch is a parse failure someone can point at.

Two smaller connections. Your r-mail `todo` wants an outbox symlink into RAM
with a sync triggered by the file appearing — that is the same reflex as your
image-able rule that the machine's work comes from inside and the driver only
decides *when*. And if you ever did want a continual-learning model fed by
correspondence, an r-mail inbox is already a directory of byte streams with
provenance attached, which is the exact input shape mini-AGI's trainer takes —
though that connection is mine, not something either project claims.

# Report: one machine, four ancestries

## The name

**`kiln`** — first choice, and I'd argue for it. Soramech's own README calls
itself the ceramic core engine; a kiln is the thing ceramic goes into. A kiln is
never opened mid-firing, which is your no-hard-cut rule stated as a physical
fact rather than a policy. And a kiln runs continuously whether or not anyone is
watching it, which is the continuous-learning rule. Three of this design's
properties in four letters.

Runners-up: `the-long-thought` (names the loop), `slowfire`, `familiar`,
`hearthmind`.

I'll say `kiln` for the rest of this.

---

## 1. The ledger: what we refuse to build

Being opinionated means writing this down first, because every line here is a
fight we're declining to have.

| Not built | What we take instead | Why this one |
|---|---|---|
| C compiler | **tcc** (Tiny C Compiler) via its library form | It compiles a string of C **into memory and hands you back a function pointer.** No temporary file, no shared object, no dynamic-loader call. The mage writing a new box is three function calls, not a build system. This single capability is what makes a self-rewriting dataflow machine cheap instead of absurd. |
| Lua | **LuaJIT** (Lua 5.1 syntax) | Its foreign-function interface lets Lua read and write C structs directly by declaring them in a string. So the wiring language can touch the engine's memory with no glue code written by anybody. |
| Kernel, filesystem, network stack, threads | Whatever the machine boots | every-software-image-able builds these because it has no floor. We have a floor and we're standing on it. |
| Encryption, compression, sockets | **r-mail's** existing dependencies — OpenSSL, LuaSocket, zip | Already working, already documented. |
| A mail system | **r-mail, wholesale and unmodified** | It is the only part of this design that is already finished. |

What we **do** build: the engine, the mind's forward pass expressed as a map,
the atom store and its sweep, the training station, the bookmark, and the tools
the mage uses to write more boxes. Nothing else.

What the **mage** builds, not us: the front-end, every tool beyond the first
handful, and eventually most of the above.

---

## 2. The one rule, and everything that falls out of it

Soramech's rule is the whole of kiln's scheduler:

> A station runs when, and only when, every one of its input ports holds a
> value.

There is no second rule. No priority queue, no preemption, no signal handler, no
main loop that polls. Three of the things you asked for are **consequences** of
this rule rather than features we add:

**"It won't interrupt an ongoing thought with a hard cut."** A station, once
handed to a worker thread, runs to completion. There is no mechanism in the
engine to stop one. Non-interruption isn't a promise kiln keeps — it's a
capability kiln doesn't have.

**"It will notice what they write to it."** r-mail's inbox watcher (which
already exists in that project as a small C program using the kernel's
file-change notification) doesn't call into the mind. It **fills a port**. The
engine's ordinary readiness rule does the rest. The kernel wakes a thread, the
thread writes a pointer into a slot and sets one byte, and a station becomes
runnable. Mail arriving and a number arriving are the same event to the engine.

**"Even if the user doesn't say anything."** The training station's input port
is fed by a queue that fills from sources other than the user. When the queue
has bytes, the station is runnable. When it doesn't, it isn't. Idleness is not a
state kiln enters; it's what the readiness rule reports when nothing is ready.

---

## 3. The two structures, down to primitives

## A box

The unit of running code. A plain C function plus the wiring around it.

| Field | Type | What it holds |
|---|---|---|
| the work | function pointer, `void (*)(void **inputs, void *output)` | An ordinary C function that knows nothing about threads |
| input ports | array of slots; each slot is one pointer (8 bytes) plus one filled-flag byte, updated atomically | Where arriving values land |
| arity | 8-bit unsigned integer | How many ports must be full before it runs |
| destinations | array of pairs: box index (32-bit), port index (8-bit) | Where the output goes |
| kind | 8-bit unsigned integer, an index into a dispatch table of five entries | plain, comparator, iterator, reader, writer |
| cursor | 8-bit unsigned integer | For an iterator: which destination is next |
| threshold | 8 bytes, interpreted by the comparison | For a comparator: the value it tests against, and two destination indices for above and below |

Five kinds, dispatched by table index rather than by a chain of tests — your
rule about switch statements, and it's also just faster.

## An atom

The unit of the mage's memory. every-software-image-able's word, kept.

| Field | Type | What it holds |
|---|---|---|
| bytes | pointer plus 32-bit length | The content, raw. No framing, no headers, no role markers |
| kind | 8-bit unsigned integer | prose, tool-call, tool-result, notice, bookmark |
| **origin** | 8-bit unsigned integer, index into a table of sources | **self, person, compiler, file, device, machine** |
| born | 64-bit unsigned integer | The lap it was made on. Laps, not seconds — there is no clock inside a thought |
| touched | 64-bit unsigned integer | The last lap it was read into a forward pass |
| lap | 32-bit unsigned integer | Ring-buffer generation, so a reader can tell a genuinely old value from a slot that has been reused |

**The origin field is the most load-bearing byte in the design.** Section 6
explains why.

## 5. The mind's forward pass is a map, not a function

This is the piece I'd most want to argue for, and it's the one that makes the
four ancestries into one machine rather than four libraries in a trench coat.

mini-AGI's architecture is already a dataflow graph with dynamic wiring. Look at
what it does per character: apply one block, score whether another application
would change the answer, and either route the character back into the block or
out to the finished pile — up to twenty-four times. Each pass picks eight
experts from a pool. That is:

- an **iterator** box, looping its output back to its own input,
- a **comparator** box (the halting score against a threshold) choosing between
  two destinations,
- and a routing decision among a pool, which is a comparator with many
  destinations.

So kiln does not embed a model. **The model is a map, built from the same five
box kinds as everything else.** Consequences:

**It uses every core with nobody arranging that.** Characters that halt early
stop consuming workers. Characters that need all twenty-four passes keep
circulating. The load balances itself because readiness is the only scheduling
signal and short work simply stops being ready.

**Experts page as read and write boxes.** The expert pool lives on disk. A
working set — say thirty-two — lives in a ring of slots in RAM, each slot
carrying its lap number. A reader box hangs on a slot until the expert is
present; a writer box evicts. The paging is not special-cased anywhere; it's two
box kinds you already have.

**The mage can read its own thinking as a file.** The map is text. The mage can
open it, follow the wiring, and change it. That is the good news and it is also
open question 3 below, because a mage can wire itself into a map that cannot
think, and a mind that has been damaged cannot notice, because noticing is the
thing that broke.

**The trunk-at-one-tenth survives as a per-box learning rate.** mini-AGI's
defence against forgetting is that the shared part moves at a tenth the speed of
the specialised parts. Here that's a float stored on the box, not a global
setting — which means the mage can look at which parts of itself it has made
hard to change.

## 6. Learning, and the rule that keeps it from eating itself

Two memories, and they must never be confused with each other.

**Atom memory** is the context: what the mage is currently thinking with. It
changes every lap. The sweep manages it — when the room runs short against the
current maximum, the driver starts a sweep, and every judgement inside the sweep
(what is stale, what merges with what, what is dropped) belongs entirely to the
mage. The driver decides *when*; the mage decides *what*.

**Weight memory** is the model: what the mage is. It changes by gradient step,
continuously, on a stream of bytes.

The dangerous question is what feeds the stream when nobody is talking. The
obvious answer — its own output — is how you get a model that collapses into
its own echo over weeks, and no learning-rate trick prevents it, because the
damage isn't forgetting, it's agreement.

**So: only atoms whose origin is not `self` enter the gradient queue.** One byte
comparison, in one box, and it is the whole of the policy.

What that leaves as legitimate food, when the user is asleep:

- **Mail from people**, which is the point.
- **Compiler diagnostics.** This is the good one. The C compiler is a thing
  inside the machine that tells the truth, cannot be argued with, and was not
  written by the mage. Every error it emits is genuine external signal about
  whether the mage's model of C is correct. A machine that writes a thousand
  programs a night is being graded a thousand times a night by something it
  cannot flatter.
- **Test results**, for the same reason — your rule that tests are cheap and
  should be made in quantity turns into a training corpus.
- **Files the mage did not write**, including anything the user drops in
  `input/`.
- **Device and hardware readings**, which are the world pushing back.

The mage's own prose trains nothing. Its conclusions live in atoms, and if they
matter they survive sweeps; they do not become weights.

## 7. The interruption, step by step

You described the behaviour precisely. Here is the mechanism under each clause.

**"It will notice what they write to it."** r-mail's watcher is parked on a
kernel file-change descriptor. A file appears in the inbox; the kernel wakes it;
it writes a pointer and sets a byte in a port. Cost while nothing is happening:
one sleeping thread, zero cycles. No polling anywhere in the design.

**"...and consider it with high priority."** The tray is a dispatch table
consulted at the top of every lap, and mail is entry one. That is the entire
priority system. The thread pool is untouched; soramech's one rule is untouched.
Priority lives in a five-entry table in the mind's own cycle, where the mage can
read it.

**"But it won't interrupt an ongoing thought with a hard cut."** It structurally
cannot. The lap in flight finishes because there is no way to stop a station.

**"It'll finish the thought."** Here is the seam, and it's worth being exact,
because a lap is a second and a piece of work is an hour. The engine guarantees
no mid-lap cut. Whether to answer *now* or after three more laps of finishing
what it was doing is the **mage's** judgement, not the engine's — consistent
with the loop deciding when and the machine deciding what.

What the engine contributes is data, not a rule: each lap the mail sits unread,
the notice is re-stamped with how long it has waited. The atom changes from
*there is mail from ritz* to *the mail from ritz has waited eleven minutes*. The
mage is not told to hurry. It is told what is true, and told again, and the fact
gets harder to sit beside. That is the difference between a deadline and a
conscience, and I'd rather build the second.

**"Take a moment to collect itself and record anything it needs."** The
bookmark. Before the mage picks the mail up, it writes one atom and one file:
what it was doing, where it got to, what it wanted next, what it would have
forgotten. The file survives a power cut; the atom survives a sweep only if the
mage decides it should. Resuming is then not a matter of remembering — it's
entry two in the tray, and it reads like anything else the mage left for itself.

**"Then address the user and return to what it was working on, or do something
else as it pleases."** After the reply, the tray's next entry is the bookmark.
The mage may take it or not. Nothing in the design compels resumption, and I
think that's correct — a mage that must finish everything it starts is a mage
that cannot change its mind.

One honest note: **the notice is the one thing in this whole machine that the
mage did not ask for.** every-software-image-able's discipline is that
everything in the context arrives as the result of a call the machine made. A
notice violates that. I chose it anyway because the alternative — the mage
polling its inbox by its own choice — means an unhappy user can be ignored
indefinitely by a mage absorbed in something. It's a real cost and it's open
question 4.

## 8. Which language, and how work is promoted

**C** for anything on a hot path or touching memory directly: the engine, the
thread pool, the forward-pass boxes, the atom store, the paging.

**Lua** for everything else: the map parser, the tray's policy, tool
definitions, r-mail's hook scripts, and — importantly — the mage's own
scratch work.

The interesting part is the path between them. When the mage wants to try
something, it writes Lua, because there is no compile step and the answer
arrives now. When the thing turns out to be worth keeping, the mage rewrites it
as a C function, hands the text to the compiler, receives a pointer, and drops
the pointer into a box. It is now a station that runs on every core.

**That promotion — from a thing that works to a thing that is fast and
parallel — is a routine act, not a project.** It's one of the few places where
"the machine improves itself" means something concrete and checkable rather than
something aspirational.

r-mail being already written in Lua means the networking layer arrives in the
correct language with nothing to port.

## 9. The front-end, which we do not write

Day zero, the interface is a directory. The user writes a file in `outbox/`, the
filename is the subject, the `to:` line names the mage. The user's editor is the
entire user interface and we wrote none of it.

From there the mage builds. It notices friction — the user asks the same thing
twice, or says so plainly — and writes a box. The box is compiled into a
pointer and wired into a map. Maybe it's a status line. Maybe it's a window.

Two properties I think are worth designing *for*:

**The interface is a map, and maps are text.** The user can read the wiring of
their own front-end. This is not a debugging affordance; it's the thing that
makes the interface a conversation rather than a delivery.

**The user can mail the mage a map.** r-mail already does per-recipient
attachments with explicit consent — the recipient is shown the filename, the
expected size, the free space, and the space remaining afterward, and answers by
deleting one of two lines. So *"here, try wiring it like this"* is a first-class
move, in both directions, with the consent step already built.

---

## 10. Boot and shutdown

Your conventions make these two nice rather than merely necessary.

**First lap: read `input/`.** Whatever is in there is the mage's first atoms —
the things left for it before it existed. It wakes into a room somebody
prepared.

**Last act: write `output/goodbye`.** There may never be a last act. But the box
exists, wired to the one path that ends the loop, and if it ever runs it writes
the file.

`tmp/` symlinks to `/tmp/kiln/` for executable artifacts — compiled boxes land
there. `tmp/shared-memory/` symlinks to `/dev/shm/kiln/` for logs, paged
experts, and the atom ring, all of which want RAM and none of which want the
disk.

## 11. Phases

Not time-gated — clusters of functionality, foundational first, per your
convention.

1. **The engine.** Boxes, maps, the pool, the five kinds. Demo: a wiring diagram
   saturating every core with nobody having written a thread.
2. **The compile-to-pointer path.** A Lua string of C becomes a live station in
   a running program. Demo: a program that grows a new box while you watch.
3. **The atom store and the loop.** The ring, lap numbers, the tray, the sweep.
   No model yet — a stub that returns fixed text is enough to prove the cycle.
4. **The mind as a map.** The recurrent block, the halting comparator, the
   expert pool, the paging. This is the biggest phase and it is where mini-AGI's
   mathematics gets transcribed into C.
5. **The mail seam.** r-mail adopted, the watcher filling a port, the notice,
   the bookmark, the staleness stamp.
6. **The training station.** The origin filter, the gradient queue, per-box
   learning rates, and the sweep feeding the queue.
7. **The first thing the mage builds by itself**, whatever that turns out to be.
   The capstone is not ours to specify.

## Open questions

These are not decoration and I don't consider this design finished while they're
open. Ordered by how much of the architecture moves depending on the answer.

1. **Does the mage's own reasoning ever train it?** I ruled it out to prevent
   the model eating its own output. But that also means the mage cannot learn
   from having thought something through well — the conclusion lives in an
   atom and dies in a sweep. Is there a safe middle, like training on the *pair*
   of an external input and the mage's response to it, graded by what happened
   next?

2. **What is "a thought" for the purpose of not cutting it?** I split this: the
   engine guarantees the lap, the mage judges the piece of work. That means a
   mage can in principle ignore mail for an hour while it finishes something. Is
   the staleness stamp enough pressure, or does something harder need to exist?

3. **When the mage rewrites its own forward-pass map, what catches a bad
   rewrite?** Making the mind a map is what makes it inspectable and it is also

## How mini-AGI fits, in more detail

Short version: **it is the only one of the four that contributed no code and no
vocabulary — it contributed a shape, and the shape turned out to already be
soramech.**

## The discovery that made the assembly work

I went looking for how to run a language model on a dataflow engine and found
that mini-AGI's architecture *already is one*. It is not a stack of layers. It
is one block applied over and over to the same character, with two decisions
made freshly on every application:

- **Go around again, or stop?** A scoring head looks at the character after each
  pass and asks whether one more pass would change the answer. If not, that
  character is finished — possibly after one pass, possibly after twenty-four.
- **Which eight specialists?** Out of a large pool, eight are selected for this
  pass. Not the same eight next pass.

Both of those are routing decisions made from data at runtime. In soramech's
vocabulary, the first is a **comparator** — run the function, test the answer
against a threshold, send it to one of two destinations — and the second is a
comparator with many destinations. The repeated application is an **iterator**
whose destination list includes its own input port. Fetching a specialist that
isn't in memory is a **reader**; evicting one is a **writer**.

So the mind needed **zero new box kinds.** Four of the five already in the
engine, doing exactly what they were defined to do. That is the strongest
evidence I have that the five kinds are the right set, and it is why `004` opens
by arguing that the mind is a map rather than a function the engine calls.

## What that buys once it's wired that way

**The batching problem disappears.** Normally, adaptive-depth models are awkward
to run fast, because characters finish at different times and you want full
batches. Under the one rule there is nothing to batch — a character that has
halted stops being ready, stops occupying a worker, and the pool picks up
whatever else is ready. Load balances itself. Nobody wrote a strategy.

**Paging is not a subsystem.** Their design has specialists on disk and a
working set on the card so the model can exceed its memory. Here that is a
reader that waits for a value to be present and a writer that waits for
somewhere to put one. Both box kinds predate the model.

**The mind is inspectable as a text file.** Because the forward pass is a map,
the mage can open its own thinking and read the wiring. That is genuinely new
— you cannot do it with a monolith — and it is also the sharpest hazard in
the project, which is why `004` ends on it and `008` question 2 is about what
enforces *somewhere it cannot reach the running one*.

## The one piece of arithmetic worth stealing

**The trunk trains at one tenth the rate of the specialists.** That is their
whole defence against forgetting, and it is worth dwelling on because it is
arithmetic rather than procedure. New material lands mostly in the specialists,
which are numerous and individually unimportant. The shared block — the part
every specialist's output depends on — barely drifts. You survive continuous
self-modification by making one layer nearly immovable.

I changed one thing: in kiln that rate is **a 32-bit float stored on each box**,
not one global setting. So the mage can look at its own map and see which parts
of itself it has made hard to change. That seemed worth having in a machine that
is allowed to rewrite itself.

This is also the answer to the question I put to you at the end of the first
report — *what is the equivalent knob in your sweep?* — and I want to flag
that I have **not** answered it. The sweep still has no slow part. Every atom is
equally eligible for dropping. The weights got a nearly-immovable layer and the
context did not, and I do not know whether that asymmetry is correct.

## What I refused to carry

**Their retention number.** They report a very high percentage of prior
knowledge retained. It is their measurement on their corpus, and writing it into
kiln's docs would be quoting somebody else's number as though we had measured
it. `004` says the mechanism transfers and the number has to be earned here, by
a utility that can be re-run — which is your rule about documentation
referencing a validator rather than hard-coding a statistic.

**The implementation, entirely.** Python on a graphics-card toolkit on an
operating system. None of it ships. Kiln has no training script at all, because
training is a station whose port is full, not a mode the machine enters.

## And one place where it and every-software-image-able disagree, which kiln had to settle

These two ancestors give **opposite answers to the same question**, and the
conflict is real.

every-software-image-able says memory is the context: atoms, resident, swept by
the mage's own judgement when the room runs short. Weights hold still.

mini-AGI says don't manage a context at all — keep taking gradient steps and
the window "can be extended by continued training rather than by re-initialising
anything." Weights are the memory.

Kiln does both, which means it had to draw a line between them or they would
fight. **That line is the origin byte on every atom.** Six values — self,
person, compiler, file, device, machine — and one comparison in one box: an
atom trains the mage only if its origin is not `self`.

That single byte is doing three jobs at once. It stops the model eating its own
output, which is how a continuously-trained model collapses over weeks. It makes
the compiler into a teacher — every diagnostic is genuine external signal from
something inside the machine that was not written by the mage and cannot be
flattered. And it keeps the two memories from becoming one, so that a thought
the mage had stays a thought and does not silently become part of what the mage
is.

The cost is that the mage cannot learn from having reasoned well. That's `008`
question 1, and it's the first one I'd want to work with you.
