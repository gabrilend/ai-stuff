## What the rungs are about


They're the machine's answer to one question it will face forever: **I want
something. How do I get it?** Four moves, tried in order, cheapest first.


| | The move | What it costs |

|---|---|---|

| 1 | Use what's already here | nothing |

| 2 | Alter something here to do it | the risk of breaking whatever depended on the old behaviour |

| 3 | Clear space, build the new thing | space, which had to come from somewhere |

| 4 | Condense — merge things that duplicate each other | verbosity |


**The whole idea lives in rung four.** When two pieces of software know how to
do the same thing, they become one piece that knows it once. What leaves the
drive is *duplication, not capability*. So the drive reaches more software over
time without gaining a byte. The document puts it in five words: **programs do
not compress; capability does.**


That's what makes the project's central instruction — *build every piece of
software imaginable* — not absurd on a finite disk. The machine doesn't store
every imaginable program. It stores the smallest set of parts that combine into
them.


**And it gives a stopping condition that nobody had to invent.** Growth ends
when building one more thing would cost a *capability* rather than a
*duplication* — when there's no verbosity left to squeeze and the next byte
has to come out of something the machine can actually do.


**Rung one needs something that doesn't exist by default.** You can't answer
"can anything I have already do this?" from a directory listing, because a
filename doesn't say what a thing can do. So the machine maintains a catalogue
of capabilities phrased so that a want can be matched against them —
searchable by task, not browsable by name. Each entry records what provides it,
what it does, what it depends on, how well it performs, and **when it was last
actually needed**. That last one is kept continuously rather than measured on
demand, because rung three needs to know what hasn't been used lately at exactly
the moment the machine is out of room — the worst possible time to start
measuring.


**The interesting part is that rungs two and four fight each other,
permanently.** Merging two specific things produces one general thing, and the
general version now has dependents with different needs — so a change made for
one of them breaks the other. Condensing makes space cheap and modification
expensive. The denser the machine gets, the more hangs off each remaining piece,
and the harder altering anything becomes. The document is clear that this isn't
a defect to design out; it's a trade the machine makes continuously, and *what
mediates it* is called the largest unanswered structural question in the whole
design.


Two things that change the character of it:


**Nothing arrives.** A "request" is the machine giving itself something to do
— the mind is a closed loop that holds its own context and re-prompts itself.
So the four rungs aren't a request handler. They're the machine's reasoning
about its own next move, for the rest of its life.


**Breakage is discovered by running, not prevented by bookkeeping.** Rung two
used to demand a complete reverse index — for every thing, what uses it —
before you were allowed to change anything. That got softened deliberately, and
your own line in the document is the argument: *"it'll fix it when it tries to
run the program again, sees that it's broken, and thinks 'oh huh I should fix
that'."* A machine with nobody waiting on it can afford to find out the
expensive way. The index became a good idea rather than a precondition.


**The bit I find most striking** is what this implies about two machines from
the same seed. One grows up in the dark, fills its drive, and *then* has a
screen plugged in. It has to prune to make room — and because it has
everything else it built as context, the software it writes for that screen is
not what a machine with a screen from the start would have written. Growing in
one order rather than another isn't a delay. It's the thing that makes each of
these machines different from every other one.


And the document is careful to say the rungs are patterns, not laws: *"a
document describing how the machine ought to be organised is a suggestion made
by someone who has not yet seen the hardware it woke up on."*
