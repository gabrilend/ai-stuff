Five, most-likely-to-pay-off first.

**1. Fix the two silent boot-path defects, this week, whatever else happens.**
The entry point throws away the handle the firmware uses to identify the running
program, and nobody disarms the firmware's five-minute watchdog. Both are an
afternoon. Both fail *silently* — the handle one by looking up whatever was
left in a register, the watchdog by resetting the machine with no message and no
relationship to what it was doing. The second one is guaranteed to fire the
moment a real model thinks for longer than five minutes, which is the first
thing a real model will do. Finding either of these at first light, on a board,
through a serial cable, would cost a day each.

**2. Then first light on real silicon.** This is the highest-information step in
the project and it is *cheap now* — the image already boots under real
firmware on three architectures, so the work is a USB stick, a spare machine,
and a serial console. The argument for it is already written down in your own
list of emulator lies: eighteen entries, each one found by a board disagreeing
with the emulator, several of them things nobody would have predicted (an image
base that is memory on one machine and nowhere on another; every symbol
reference silently becoming zero once the linker was gone). Every part of this
project has been tested alone under emulation. Until a real machine starts, "it
works" means "it works in a simulation of a machine whose disagreements you have
already catalogued eighteen times."

**3. While waiting for hardware: teach it to read a disk before writing to
one.** The capstone is *install yourself without destroying what is already
there*, and its most dangerous instruction is a partition table write — get it
wrong and every partition on the disk is gone at once. The reading half needs no
board at all: parse a partition table, then the allocation structures inside
each filesystem, and answer one question — which blocks are spoken for. FAT
keeps it in the allocation table, ext in block bitmaps, NTFS in a bitmap file,
and reading any of them is far less work than writing one. This is the only
piece of the capstone buildable today, and it is the piece you least want to be
writing for the first time with a real disk attached.

**4. The thinking loop on the second architecture.** Biggest volume of remaining
work, and the most mechanical: there is already a working twin on the first
architecture, and a harness that holds a port to bit-identical scores over a
whole forward pass. It also ends a genuinely silly situation — the
loop-and-its-limits ticket spent four days waiting on work that belonged to no
ticket at all, because "that's the other porting ticket's kind of work" got read
as naming an owner. Do this when you want progress; do the three above when you
want to learn something.

**5. The unique one: stop planning to compare strings in assembly three times.**
The chip-side hands are described as the least pleasant work left, and the
reason is a single design choice — recognising a tool request means matching
byte strings, in assembly, once per architecture. But this project already
solved exactly that problem once. The engine's think-time half was written never
to touch a string, and the cost was moved to startup, where a routine builds
prepared lookup tables out of the word-lists the model carries. The tool
catalogue is the same shape of problem: a fixed set of names, known at build
time, matched at think time. Build the catalogue into a table at startup and the
think-time side becomes an index into a dispatch table rather than a string
comparison — which is both the cheaper thing on the metal and the thing you
only have to get right once instead of three times.

Each of these wants a ticket before any code; the first-light and install ones
already have theirs, and the catalogue idea would be a change to what the hands
ticket says rather than a new one.

A question back, because I think it's the real one here: the
firmware-can't-find-anything bug went unnoticed for days because the builder's
layout matched what the engine looked for *exactly* — both halves were right
about their own half, and nobody asked the firmware, which was the only
component that had to find the first byte. What else in this project has that
shape? Where else are two parts agreeing perfectly with each other while a third
party that was never consulted gets the final say?

### Assistant Response 3

> Answering the token question first, then I'll start on the bugs.

Two bugs fixed and proved on the emulated board; the long watchdog sit is still
running. Answering your token question while it finishes.

**Yes — the vocabulary is the better answer, and it's already on the card.**
The model carries a list of every token it knows: a short byte string and a
number for each. The tokenizer's prepared tables are built from that list at
startup, so the machine already owns it.

That changes the shape of the problem. Right now a tool call would be recognised
by looking at the *text* the machine produced and comparing byte strings. But
the machine never actually produces text first — it produces a token number,
and only turns that into bytes at the very end, to say it aloud. So if each
tool's name is stored as the **token numbers it spells**, worked out at build
time by running the tokenizer over the name, then recognition happens one number
at a time as the words are drawn, and no string is ever compared. The first
token of a name indexes a dispatch table directly, which is the thing you'd want
anyway.

Three things that have to be true for it to work, all checkable at build time:

- **The same name can spell differently depending on what surrounds it.** A word
  with a leading space is a different token from the same word without one, and
  what follows can change where the split lands. The fix is to pin the syntax
  — a tool call always starts at a fixed marker at the start of a line and
  ends at a fixed delimiter — so the surrounding bytes are fixed and each name
  has exactly one spelling.
- **Two tools must not spell the same, and one must not be a prefix of
  another.** The build tokenizes every name in its pinned context and refuses to
  build if either happens, which is this project's existing habit for seam
  problems.
- **The table is model-specific.** Token numbers belong to the vocabulary that
  produced them, so swapping the model changes every number. That means the
  catalogue on the card has to be generated beside the tokenizer tables from the
  same model, never written by hand — otherwise it silently points at the
  wrong words.

## What's done so far on the bug fixes

Both on the machine that ships, first architecture, emulated:

- **The firmware's name for the running program is kept**, stored into the work
  area before the first thing is said — that ordering matters, because saying
  anything is a call into firmware whose own first argument travels in the same
  register the handle arrived in.
- **It's spent immediately on proving it's the right handle**: the machine asks
  firmware where it placed this program, and requires the address the code is
  actually standing at to fall inside that span. Saving the wrong register
  instead makes the lookup refuse and the machine stop before it thinks — I

- **The five-minute timer is disarmed.** Proved twice: firmware returns success,
  and — more usefully — I armed it deliberately for thirty seconds and

  watchdog reset makes it *exit* rather than restart, and the reset is invisible
  in anything the machine said. The test now measures how long the emulator
